# Атлас System One — реализация этапов исследования

Это операционные рецепты к [общему плану](system-one-atlas.md), а не сообщение
о выполненных экспериментах. Все имена будущих модулей, manifest и наборов данных
ниже — **проект артефактов**, пока их реализация и конкретные значения не проверены.
Отдельное последующее выполнение — [offline пилот 19.10.2026](system-one-pilot.md):
проверенные код, данные, raw результаты и оставшиеся препятствия указаны там;
оно не означает завершения P0–P10 или native online серии.
Не следует запускать придуманные команды: исполняемые entry points появляются
только вместе с кодом и его проверкой. Актуальные задачи и владельцы — в
[wiki](README.md#ближайшие-задачи); здесь описаны зависимости и критерии готовности.

## P0. Вопрос и контракт

[Анимированная иллюстрация P0](../research-atlas/phase-00.html).
**Вход:** поручение инициатора, действующая постановка, контракт v0, ограничения
оборудования и личный вклад адаптации. **Владелец результата:** инициатор;
контракт согласуется с участниками отбора и маршрутизации.

**Действия.** Выписать одну заменяемую операцию: оценка полезности каждой уже
наблюдаемой KB-единицы относительно текущей потребности. Уточнить рубрику полезности:
содержит ли фрагмент применимое правило, исключение, требуемый факт или средство
устранить неопределённость текущего шага. Несколько кандидатов могут быть полезны
одновременно, поэтому softmax по всему пулу не заменяет независимые бинарные pᵢ.
Различить `irrelevant`, `useful`, `uncertain`; неопределённость не превращать в 0.

Зафиксировать A/B/C и N/H, общие условия, главный контраст B↔C, offline и online
единицы анализа. Указать, что default — опубликованный checkpoint без нашей
адаптации, а не случайно инициализированная модель. Сформулировать H1–H5 и
заранее описать, какой результат их не поддержит. Выбрать первичную метрику Q
и допустимую потерю δ с научным смыслом; не брать δ из увиденного test.

Определить границы самостоятельного вклада: адаптация C; packer, state extraction
и маршрутизатор R фиксируются в основном опыте. Сравнение функций потерь и
reasoning формулируется отдельными факторами, а не названием одного метода.

**Выход:** protocol version, таблица arms, словарь событий/метрик, rubric v0,
решение о первичном контрасте и перечень открытых параметров. Каждый численный
параметр имеет статус «предложение» или «закреплено до test» и источник решения.

**Проверка:** два читателя одинаково классифицируют 10–20 учебных примеров и
могут указать, что именно меняется между B и C. Это предложение размера smoke audit.
**Стоп/альтернатива:** если метка неоперациональна, сначала сузить задачу до
evidence usefulness; не запускать обучение на суррогате без названия и проверки.

## P1. Аудит стенда и моделей

[Анимированная иллюстрация P1](../research-atlas/phase-01.html).
**Вход:** P0, upstream τ-bench/τ²-bench, model cards, training code и статьи.

**Действия.** Зафиксировать репозиторий, commit, domain, tasks/KB/policy/tools/evaluator
hashes и runtime. Не смешивать исходный τ-bench 2024 с τ-knowledge из современного
τ²-bench: похожее имя не означает одинаковые задачи и протокол. Проверить фактический
список task IDs и происхождение split. Проверить лицензии отдельно для кода,
данных, весов и созданных teacher outputs; не считать лицензию библиотеки лицензией
всего downstream corpus. Записать дату доступа и разрешённое распространение.

Для кандидата компактной модели проверить end-to-end inference на полном
сериализованном `(state, candidate, labels, instructions)`; измерить токены
её tokenizer, пиковую память и batch latency. Протестировать границы окна без
silent truncation. Различать заявленное/served окно и валидированное качество.
Проверить один training step: loss конечен, градиент ненулевой, параметры
обновились, checkpoint сохраняется/загружается и меняет прогноз воспроизводимо.
Такая проверка ещё не доказывает улучшение качества.

Для LLM выбрать точную версию, provider, режим reasoning и лимиты. Если snapshot
не доступен через API, сохранять alias, дату, returned model ID, provider и
отмечать невозможность строгого повторения backend. Зафиксировать одинаковую
модель simulator/evaluator во всех сравнениях. Учесть обязательные поля истории
reasoning и tool calls у provider; не стирать их незаметно в одной ветке.

**Выход:** source manifest, compatibility report, hardware profile, модель-кандидат
для основного опыта и один резервный вариант. **Критерий:** подтверждены native
runner, readout вероятностей и реальный путь обновления весов выбранной модели.

**Стоп/альтернатива:** если текущий API модели не поддерживает fine-tuning, сначала
проверить публичный trainer. Замена на другой encoder — отдельная модельная линия,
а не adapted версия прежнего checkpoint. Если inference не помещается, уменьшить
общий допустимый input по заранее установленному правилу или выбрать модель;
не обрезать отдельные arm по-разному.

## P2. Минимальный harness

[Анимированная иллюстрация P2](../research-atlas/phase-02.html).
**Вход:** проверенная версия τ²-bench, контракт P0, manifest P1.
**Ответственность:** общий компонент команды; инициатор отвечает за адаптационный
интерфейс и воспроизводимость своего использования.

**Действия.** Сначала воспроизвести native episode и получить штатный reward/trace.
Затем добавить agent adapter, который получает только разрешённые наблюдения.
Хранить append-only raw history; отдельно построить observed_pool с provenance и
дедупликацией по ID+content version. Сформировать immutable snapshot и общий hash.
State extractor фиксирован и не вызывает отдельную LLM-сводку.

Сделать три реализации scorer интерфейса: LLM, frozen compact, adapted compact;
на этом этапе adapted может быть только будущей точкой подключения, её нельзя
отмечать работающей. Добавить детерминированный packer и проверку бюджета готового
payload. Model projection заменяет только retrieval bodies квитанциями, сохраняет
call IDs/roles/non-KB responses, вставляет выбранный evidence block один раз.

Native actor продолжает диалог и вызывает tools. Отдельный evaluator получает
свой штатный контекст, но scorer не получает Task/gold/future/hidden corpus.
Встроить trace emitter с таймингами, usage, cache, retries и причинами отказов.
Технический fallback использует тот же snapshot, а его затраты включаются в arm.
Ранжирование вероятностей не превращается в риск-гейт само собой.

**Выход:** adapter/scorer/packer/projection/trace modules и маленькие воспроизводимые
fixtures с настоящими формами native сообщений. Предлагаемые интерфейсы и точки
расширения — в [техническом приложении](system-one-atlas-architecture.md).

**Критерий:** проходят тесты mixed tool batch, no hidden data, state update,
content version, exact token boundary, duplicate evidence, invalid IDs, timeout,
NaN и exhausted fallback. No-op projection не меняет native поведение на fixture.
**Стоп/альтернатива:** нарушение инварианта tool history блокирует сбор данных;
не чинить его удалением неудобных tool calls или отключением evaluator.

## P3. Разделение задач

[Анимированная иллюстрация P3](../research-atlas/phase-03.html).
**Вход:** inventory реальных задач и правил P1; labels и траектории ещё не собраны.

**Действия.** Создать task-family graph: общий шаблон запроса, policy scenario,
связанные entities, почти одинаковые формулировки/решения. Применить grouping
и проверить компоненты вручную. Все turns, retries, paraphrases, teacher answers
и synthetic descendants одной группы наследуют её split.

Рабочее предложение — train/dev/test около 60/20/20 по независимым группам, а не
случайно по парам. Фактические количества становятся известны после аудита.
Если групп мало или одна группа слишком велика, сохранить связность и показать
дисбаланс; не разрезать её ради красивой пропорции. Dev выделить для выбора
гиперпараметров; при необходимости отдельный calibration subset либо grouped
cross-validation внутри train/dev. Final test отделяется один раз.

KB может быть общим доменным справочником по native правилам; это same-domain
setting, а не гарантия unseen knowledge. Совпадение KB-текста, input пары и
task template — разные виды пересечения, их отчёт ведётся отдельно. Hidden gold
допускается только в закрытом offline процессе подготовки train labels/оценки
с контролем происхождения, никогда в входах рабочего агента.

**Выход:** split manifest с IDs, family IDs, seed, hashes, алгоритмом и ручными
исключениями; leak report; перечень запретов на использование test.
**Проверка:** ни одна ancestry group не пересекает split; exact и near-duplicate
пары проверены; test IDs не появляются в teacher train job и HPO manifest.

**Стоп/альтернатива:** full published 97-task оценка не является независимым test,
если часть этих задач использована для обучения. При нехватке данных использовать
grouped cross-validation для разведки и отдельный небольшой holdout с широкими CI;
не обещать прежнюю сравнимость с leaderboard. Synthetic examples увеличивают
число примеров, но не число независимых задач.

## P4. Сбор наблюдений

[Анимированная иллюстрация P4](../research-atlas/phase-04.html).
**Вход:** working harness P2, sealed split P3, лимит будущей серии.

**Действия.** Начать с native и дешёвого/LLM baseline collector на train/dev,
с заранее заданными task IDs, seeds, actor/simulator versions и retry policy.
Сохранять не только успешные эпизоды: ранние ошибки и трудные состояния нужны
для оценки границ. У каждого episode — immutable raw trace и runner outcome.

После каждого нового KB batch сохранить snapshot до следующего actor call:
cutoff, state fields с provenance, весь observed_pool, hashes и exact serialization.
Не добавлять в pool документы, которые среда не вернула агенту. Не подменять
старое наблюдение новой редакцией по тому же ID. Упаковка используется для
выполнения, а full observed_pool сохраняется для последующего разбора.

Контролировать частоты сценариев, длины состояния/кандидата, пустые пулы,
переполнения, дубли и систематические ошибки парсинга. Отметить collector policy
в dataset card: один teacher генерирует смещённое распределение состояний.
При добавлении другого collector сохранять источник и сравнить покрытие;
смешивание не превращает записи в независимые task samples.

**Выход:** episode manifests, raw trajectories, snapshot index, parser diagnostics,
usage ledger. Тела данных — вне Git с checksum и доступным команде хранилищем;
в Git — схемы, разрешённые примеры, metadata и команды после появления кода.

**Проверка:** из raw trace повторно строятся те же snapshot hashes; cutoff
исключает будущее; каждый candidate ссылается на наблюдение; число пропущенных
или повреждённых записей явно опубликовано. **Стоп:** превышение лимита расходов,
утечка test, изменение provider/model или parser regression останавливает job.
Повтор оформляется новым run ID; сырой результат не переписывается.

## P5. Разметка и датасет

[Анимированная иллюстрация P5](../research-atlas/phase-05.html).
**Вход:** train/dev snapshots, rubric P0 и происхождение всех наблюдений.

**Действия.** Сначала создать небольшой вручную проверенный audit set с полезными,
неполезными и неоднозначными фрагментами. Независимо разметить часть примеров
двумя читателями; сохранить disagreement и adjudication. Не считать учителя
золотым стандартом по факту высокой уверенности.

Для масштабирования применить teacher к `(state, candidate)`, сохранив model,
prompt, raw response, reasoning mode и расходы. Полезность проверять по тексту
правила, применимости к фактам и информационной потребности. Для subset провести
counterfactual проверку набора: при одинаковом состоянии/seed сравнить включение
и удаление evidence. Стохастический rollout даёт оценку эффекта, а не абсолютный
oracle; дубли и взаимодействия фрагментов могут скрывать необходимость каждого.

Формировать hard negatives из observed_pool: близкая тема с неверным типом
счёта, исключение с неподходящим условием, неприменимая к текущему состоянию версия.
Дублирование применимого правила само по себе не делает candidate отрицательным:
избыточность относится к составу набора и оценивается отдельно. Не брать произвольный hidden corpus
как будто он был доступен агенту. Частоты классов и веса sampling фиксировать;
на test сохранять естественную или явно описанную оценочную выборку.
Resampling меняет доли классов и распределение оптимизируемого риска:
зафиксировать целевую популяцию, выборочные веса и отдельно оценивать
калибровку на её отложенной выборке. Balanced train сам по себе не делает
вероятности откалиброванными для естественной частоты полезных фрагментов.

Отдельные таблицы: candidate labels, set sufficiency labels, native episode
outcomes. Success episode нельзя размножить как y=1 на все его chunks. Uncertain
примеры исключать из primary hard-label loss по явному правилу либо моделировать
как soft labels в отдельной абляции; не подменять несогласие вероятностью истины.

**Выход:** dataset card, rubric version, annotation lineage, train/dev manifests,
class/length/source distributions, quality audit и frozen preprocessing.
**Критерий:** известны оценка ошибок меток и интервалы/ограничения, все входы
не содержат labels/rationales/gold; дубликаты не пересекают split.
**Стоп/альтернатива:** если labels невалидны, уменьшить объём и повысить ручную
проверку; большой шумный набор не считать достаточным основанием обучения.

## P6. Baseline и default System One

[Анимированная иллюстрация P6](../research-atlas/phase-06.html).
**Вход:** P2 и проверенные данные P5. **Цель:** проверить весь измерительный тракт
до дорогой адаптации и получить содержательную точку отсчёта.

**Действия.** На одинаковых frozen snapshots оценить BM25/recency, основной
LLM joint selector A и default compact scorer. A выдаёт упорядоченные IDs,
которые проходят общую проверку допустимости и бюджета. Для диагностического
сравнения оценщиков добавить отдельный A-pointwise с выходом p(useful).
Указать prompt/label descriptions: default не значит
отсутствие настройки входа, поэтому prompt выбирается по train/dev и затем
замораживается. Один packer и tie-breaking используются в B/C, дешёвых
ranking-контролях и A-pointwise; общий бюджет и информация сохраняются также
в joint A, который сам предлагает набор.

Посчитать Brier/NLL для probabilistic arms, PR-AUC, ranking/coverage и полноту
evidence set. BM25 scores не выдавать за вероятности; для него ranking/set/episode
метрики достаточны. Не сравнивать NLL по разным ground-truth определениям.
Сохранить штатную temperature default checkpoint как B-published. Дополнительно
сравнить raw B/C и одинаково откалиброванные B+TS/C+TS, используя один отдельный
calibration subset и одинаковое правило подбора temperature. Не приписывать
обновлению весов эффект temperature, изменённой только у adapted модели.

Запустить небольшой dev online pilot N/H/A/B. Измерить успех, ошибки policy/tools,
длину эпизодов, частоты вызовов/fallback и полные расходы. Удерживать одинаковый
actor/simulator/evaluator, задачи и seed schedule; порядок arm по возможности
перемешивать, чтобы дрейф provider или нагрузка не совпали с методом.

**Выход:** baseline report, проверенный usage accounting, распределения latency,
прогноз стоимости полной серии. Не перенести dev цифры в график final test.
**Критерий:** native reward корректно считывается, failed/timeouts не потеряны,
цена scorer включена; offline и online истории помечены отдельно.
**Стоп/альтернатива:** если BM25 уже выигрывает и обучение не обещает улучшения,
это основание сузить/переосмыслить гипотезу, а не убрать дешёвый baseline из статьи.

## P7. Дообучение и абляции

[Анимированная иллюстрация P7](../research-atlas/phase-07.html).
**Вход:** frozen checkpoint, dataset v1, baseline P6 и измеренный training budget.

**Действия.** Первый опыт — CE на проверенных hard labels без rationale в student
input. Сначала smoke step, затем небольшой train subset, затем разрешённая серия.
Сохранять seed, optimizer, learning rate, schedule, batch/accumulation, epochs,
precision, trainable layers, tokenizer, data order, hardware и checkpoint lineage.
Не предполагать, что LoRA поддерживается конкретным нестандартным encoder.
Сравнение head-only и encoder adaptation — самостоятельная ось, если оно нужно.

Повторить Brier-only с той же инициализацией, данными, числом примеров/шагов и
сопоставимым HPO budget. Одинаковый learning rate — полезный контроль, но разные
масштабы gradient могут требовать равноправного dev search для обоих losses.
Не считать флаг CE+λBrier чистым Brier. Проверить реализацию формулы на малом
ручном примере и finite gradients. Смешанный loss — дополнительный arm с явно
записанным λ. Early stopping и победитель выбираются до final test.

Предложенная основная матрица: frozen, adapted-CE, adapted-Brier; желательно
несколько независимых training seeds по бюджету. Учитель с рассуждением/без
рассуждения — следующий 2×2 опыт: teacher mode × student loss. При этом student
в обоих случаях выдаёт p напрямую. У учителя одинаковая наблюдаемая информация,
model snapshot и сопоставимый лимит генерации; расход и фактические tokens
публикуются. Эффект teacher quality может быть медиатором, его надо измерить.

Reasoning на inference у decoder — другой эксперимент. Compact encoder нельзя
переключить в CoT тем же флагом. **OpenJev-RLCD** включает rollout rationale,
readout и score-function обучение генерации; это другая модельная линия/teacher,
которая не изолирует лишь смену CE на Brier. **Laya/SBERT2S1-RLCD** использует
возмущения logits и составной proper-score reward без текстового rationale.
Для этой ветки сравнивать прямую оптимизацию той же функции, PG-LOO и Reparam;
не называть её автоматически Brier-only. Distillation в compact student
оценивается отдельно. Основания и ограничения — в
[проверке источников](system-one-atlas-evidence.md#3-что-в-открытом-training-коде-подтверждено).

**Выход:** checkpoints, training manifests, learning curves, dev selection ledger,
loss audit, adapter compatibility. **Критерий:** положительный или отрицательный
dev эффект измерен, а финальный набор конфигураций заморожен.
**Стоп/альтернатива:** нет надёжных labels, OOM, нестабильный loss, отсутствие
dev улучшения после ограниченного search или исчерпан бюджет — остановить
расширения, сохранить причины и завершить основной сравнительный опыт.

## P8. Закрытая итоговая оценка

[Анимированная иллюстрация P8](../research-atlas/phase-08.html).
**Вход:** sealed final configs/checkpoints, test manifest, analysis plan,
зафиксированная δ, разрешённый расход и остановка.

**Действия.** Сначала подтвердить hashes и отсутствие test в training/HPO.
Выполнить одинаковую test task-seed матрицу для A/B/C и N/H. Повторы считаются
внутри задачи; все arm используют одну схему simulator seeds, но их диалоги
могут расходиться после первого различия. Не требовать одинакового числа turns
как условия справедливости; учитывать его как часть результата.

Разделить offline оценку на фиксированных наблюдениях и on-policy closed-loop
эпизоды. Успех native evaluator — первичная agent метрика; tool/policy ошибки,
retrieval failures и качество контекста объясняют эффект. Вывести cost per attempted
episode, total cost / number successful episodes и отдельно стоимость user
simulator/evaluator как цену исследования. При нуле успехов cost per success
не конечен, а не равен нулю.

Для разности методов использовать парные оценки по задачам; доверительные
интервалы bootstrap группировать по task/family, не по chunks. Training seed
variability и simulator variability отражать отдельно. Заранее указать primary
contrast, secondary contrasts и способ обращения с множественными сравнениями.
Не считать каждый turn новой независимой задачей.

**Выход:** immutable run manifest, raw/aggregate metrics, paired differences,
95% CI с описанным методом, failure inventory, reproducible analysis script.
**Критерий:** на каждом графике есть unit, n задач/групп/seeds, split и версии;
нет исключённых неудобных failures. **Стоп/альтернатива:** сбой измерения требует
нового прогона с записью причины; после просмотра test нельзя бесшумно выбрать
другие гиперпараметры и назвать повтор независимой оценкой.

## P9. Устойчивость и экономика

[Анимированная иллюстрация P9](../research-atlas/phase-09.html).
**Вход:** primary results P8 и predeclared sensitivity plan.

**Действия.** Проверить бюджет контекста (например, предложенные 1024/2048/4096),
длины входа, редкие policy exceptions, ошибочные/пустые retrieval, качество на
сценариях с несколькими необходимыми фрагментами. Эти числа — профили, а не
измеренный optimum. Не выбирать лучшую test конфигурацию как новый primary.

Проверить вероятность technical fallback и цену его двойной работы; разложить
полную latency на preprocessing, очередь/сеть, scorer, packer, actor, tools и
retries. Замерять wall-clock после синхронизации устройства, cold start отдельно
от steady state. Batch throughput и online single-episode latency не смешивать.

Построить quality–cost и quality–latency Pareto plots по фактическим наблюдениям
с CI. Отдельно посчитать цену teacher data, manual labels, HPO и GPU train;
сравнить service inference и total research budget. N* считать лишь при
положительной разности цены и допустимом качестве; при малой/неопределённой
экономии публиковать диапазон или отсутствие устойчивой оценки окупаемости.

Опционально проверить другой домен как external validation, не смешивая его
с исходным same-domain вопросом. Риск-гейт R сравнивать в отдельной серии
при фиксированном C и независимой calibration; это вклад маршрутизации.

**Выход:** robustness report, cost model, failure taxonomy и ограничения
обобщения. **Критерий:** основной вывод не держится на одном удобном budget,
игнорировании fallback или неподтверждённом тарифе. **Стоп/альтернатива:**
неустойчивость — часть результата; не прятать её выбором единственного среза.

## P10. Выводы, воспроизведение и ВКР

[Анимированная иллюстрация P10](../research-atlas/phase-10.html).
**Вход:** P0–P9, источники с версиями, разрешения на распространение, правила ВКР.

**Действия.** Составить evidence ledger: каждое утверждение → таблица/график →
analysis version → run IDs → model/data/split manifests. Разделить «наши
измерения», «результаты авторов», «интерпретация» и «не проверено».
Для каждого H написать поддержана/не поддержана/недостаточно данных и объяснить
область применимости. Не заменять отсутствие значимости утверждением о равенстве.

Пакет воспроизведения содержит окружение/lockfile, конфигурации, происхождение
данных, split/checkpoint hashes, инструкции получения разрешённых assets,
команды реального кода и небольшой smoke example. Секреты, персональные данные,
веса и большие сырые выгрузки в Git не включаются. Проверить воспроизведение
из чистого окружения хотя бы одним участником; если доступен только автор,
честно обозначить ограничение самостоятельной проверки.

Предложенная структура текста: постановка и ограничения; обзор typed decisions
и адаптации; формальная модель/гипотезы; данные и предотвращение утечки;
архитектура и реализация; протокол опытов; результаты с CI и ошибками;
экономика/ограничения; заключение и личный вклад. Требования оформления и
академические согласования берутся из [реестра ВКР](vkr.md), а не из атласа.

Обновить HTML-карты фактическими статусами и ссылками на результаты. Анимации
остаются объяснением, не заменяют raw metrics. Сохранить отрицательные прогоны,
исправления версионировать. Публикацию репозитория, статьи и отправку материалов
выполнять только в пределах отдельного поручения.

**Выход:** воспроизводимый исследовательский пакет, текст ВКР, материал доклада,
явное указание общего/личного вклада и AI-помощи. **Критерий завершения:**
получены постановка, воспроизводимый агент, измерения и честное сравнение;
положительный эффект, RLCD и статья не обязательны для завершения.
