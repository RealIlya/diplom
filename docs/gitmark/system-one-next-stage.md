# Следующий этап: данные и инфраструктура экспериментов

## Согласованная цель и границы

Источник — обсуждение с инициатором 26.10.2026 после завершённого
[пилота адаптации](system-one-pilot.md#kev-head-adaptation). Инициатор согласился
с целью подготовить протокол следующего опыта: проверить пользу адаптации
KEV-0.8B сверх настройки frozen-модели и влияние на качество, стоимость и
задержку полного агента. Уточнения имеют приоритет над прежним предложением
начать только с локального ускорения:

- **Существенное расширение датасета обязательно.** В продолжении инициатор
  подтвердил рабочий ориентир1–3тыс. размеченных пар с промежуточными версиями.
  Квоты и состав ещё не выбраны. Существующие данные и результаты сохраняются.
- **Текущий этап — построение инфраструктуры тестов и определение направления.**
  Доказанный выигрыш агента не является условием продолжения этого этапа.
- Нужно проверить обработку нескольких фрагментов одним запросом с выбором
  любого полезного подмножества, например из пяти кандидатов. Инициатор
  подтвердил основной формат: общий state с несколькими Noul-вопросами;
  batch прежних входов остаётся контролем. [Решение](README.md#wayfinder-multi-candidate).
- Следующие эксперименты должны подвести к выбору темы ВКР и дать материал
  хотя бы для небольшой научной статьи. Тема, новизна и факт публикации пока
  не установлены; отрицательные результаты сохраняют научную ценность.
- Инициатор указал «1 или2$ лимит по api в день» и поручил получить полезный
  объём в этой сумме. Для новой серии агент принимает консервативный потолок
  **$1 суммарно на все API в календарные сутки Asia/Novosibirsk**; $2 не использует.
  Это отдельное новое бюджетное указание, не сброс/перераспределение старых caps.

Канонические вопросы, зависимости и будущие решения ведутся в
[карте следующего этапа](README.md#wayfinder-next-stage). Этот документ хранит
контекст и проверенные факты, не второй список задач реализации.

## Несколько кандидатов одним запросом: аудит исходников26.10.2026

Это статическая проверка сохранённого source, не измерение скорости, качества
или памяти. Закреплённый KEV commit
`2ecafc49fe1e8945cd600443e6c04c1cf0b3a78f`, Laya commit
`68804629e8ccd9d616d48a40e87de9fabbeae069`.

| Формат | Смысл результата | Статус |
| --- | --- | --- |
| Один Choice, пять альтернатив | Взаимоисключающие варианты, softmax с суммой1 | Есть в KEV; не выбирает произвольное подмножество |
| Пять Noul-вопросов при общем state | Пять отдельных p(useful), выбор0–5 | Есть в native KEV API/MLX; текущий wrapper не использовал |
| Batch пяти прежних бинарных входов | Пять отдельных решений с повторённым состоянием | Laya имеет predict_batch; для нашего runner нужна обвязка |

Таким образом, желаемая семантика — **многометочный отбор**, а не один
многоклассовый выбор. В KEV `SystemOneRequest` содержит общий `state` и словарь
`questions`; каждый Noul имеет собственный бинарный выход. Сумма вероятностей
по разным документам не обязана равняться1.

MLX сначала вычисляет общий state-prefix, затем независимые ветки на копиях
кеша. Это один вызов интерфейса/forward, но prefix и ветки требуют вычислений;
ветки могут делиться на несколько проходов по внутреннему token budget.
Пятикратное ускорение или снижение памяти этим аудитом не установлены.

В нашем старом runner документ находится внутри state, а scorer вызывается
для каждого кандидата отдельно. Перенос документа в отдельную ветку вопроса
меняет сериализацию входа: сохранение качества и пригодность прежней
адаптированной головы нужно проверять. Обязательность нового обучения из
исходников не следует. Если все пять документов помещать в общий state,
каждое решение видит весь набор; это отдельная постановка с дополнительными
ограничениями длины. Прежние независимые метки не описывают дубли и
взаимодополняемость документов в наборе.

В Laya есть batch отдельных входов; аналогичное переиспользование causal
prefix не подтверждено. Поэтому «один запрос», «один batch», «один проход
backbone» и «совместное рассмотрение набора» необходимо различать в опыте.

## Рабочее направление, ещё не протокол

Расширение данных и проверка группового интерфейса — параллельные предпосылки
следующей серии. Состав инфраструктуры определяется ими, затем закрепляются
сравнения, метрики, бюджет и stop rules. Возможные исследовательские оси:
зависимость эффекта адаптации от объёма разметки; перенос на новые семейства;
качество/стоимость групповой оценки относительно покандидатной.
Основной вопрос для статьи ещё предстоит выбрать.

RLCD, новая архитектура и аренда GPU не обязательны заранее. Старые протоколы
не меняются, новые платные вызовы этой картой не запускаются. Прежние лимиты и
разрешения сохраняют исходную область действия; новый дневной лимит относится
к следующему этапу и учитывается совместно с уже сделанными за день вызовами.

**Границы результата.** Это первая train-ступень к ориентиру1–3тыс. пар,
а не выполненный весь план расширения. Новое обучение и сравнение качества
моделей не проводились. Независимая оценка не выросла; при следующем пакете
нужно определить квоты полезных примеров/состояний и будущий holdout по
[открытому вопросу данных](README.md#wayfinder-expanded-data).
Новые hard-метки преимущественно отрицательные (152 из181); одно увеличение
числа строк не доказывает улучшение отбора или агента. Групповой формат уже
ускорил локальный пилот, но большой сдвиг от смены сериализации требует
отдельной проверки качества и калибровки до переноса прежней головы.
