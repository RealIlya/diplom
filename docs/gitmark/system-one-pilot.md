# Пилот System One: технический результат и граница вывода

**19.10.2026, по поручению инициатора:** реализован воспроизводимый локальный
offline стенд, проверены опубликованные веса и реальное head-only CE обучение.
BM25, frozen и CE сравнены на одном ограниченном dev snapshot. **Научный пилот
доменной адаптации пока заблокирован:** после admission dev представлен одной
группой, независимая проверка меток отсутствует, соответствие архивных task ID
закреплённым задачам не подтверждено. Native агент и его итоговая экономия не
объявляются работающими или измеренными.

Решение: сохранить Laya multilingual как технически работоспособного кандидата;
следующим опытом проверить валидный источник состояний и рубрику в нескольких
dev-группах, прежде увеличения обучения. К RLCD, Brier-абляциям и HPO не переходить.
В offline-опыте 19.10 API и аренда GPU — **0**. Отдельный разрешённый
API-пилот 25.10 завершён до очереди human review: [раздел 10](#api-implementation-v1).

## 1. Что реализовано и откуда взяты данные

Код (`scripts/system_one_pilot/cli.py`) предоставляет prepare → replay → audit
→ fit; инструкция воспроизведения (`experiments/system-one-pilot/README.md`)
и закреплённый профиль (`experiments/system-one-pilot/config.json`) содержат
реальные команды. Отдельный fetch проверяет контрольные суммы публичных входов.
Выходные файлы создаются без перезаписи; неудачные и ранние попытки сохранены.

Стенд строит snapshot перед assistant call, после полного tool batch. Исключает
приватные user tools и будущие события; input собирается по allowlist, без Task,
reward, required_documents и rationale. Хранятся raw видимая история, provenance,
версии документов и hash snapshot. KB тела превращаются в квитанции в state;
не-KB результаты, включая shell, сохраняются. Проекция поддерживает no-op и mixed
batch, но **не подключена к живому native runner**. Это не эмуляция agent reward.

Источник наблюдений — опубликованный неизменяемый префикс **20 000 000 байт**, SHA
`4d7f30616a6c158079d1569e8213fbad20518d7725284af197d1383459ebe993`.
Декодированы только **52 полных** эпизода; оборванный последний объект исключён.
Восемь test-эпизодов не извлекались; 14 повторных эпизодов тех же задач пропущены.
Остались 30 snapshots, 783 candidate chunks: **619 train, 164 dev**.
Chunks — до 100 слов с исходными character offsets и видимым заголовком;
полный input `(instructions, labels, state, candidate)` проверяется tokenizer.
Shell-текст не обрезается ради попадания в окно; отсюда значительная часть отказов.

Архив сообщает actor `openai/responses/gpt-5.4`, reasoning xhigh; simulator
`gpt-5.2`, reasoning low, seed 300, retrieval **AllTools**, commit
`1ba0913b59351dd87fcdd04008280c6c4cfb71f2`. Это чужие ранее оплаченные эпизоды,
не наши новые rollouts. Их исходная цена неизвестна. Полный returned info и все
usage-поля доступны в локальном replay manifest; новый API ни разу не вызывался.

Рабочая ревизия проекта — τ `4ce7c0397c1eb65c9bbe59aeacfe1ca44a1cd699`, 97 задач,
698 документов; для целевого native опыта остаётся профиль **bm25**. Проверено
266 наблюдаемых document versions: 253 текста точно совпали с текущим KB,
13 отличаются (6 document ID), неизвестных ID нет. Старые тела не подменялись
новыми. Загрузка tasks.json старой ревизии дала **HTTP 404**, git-tree API —
**HTTP 422 / Invalid object requested**. Это подтверждает отсутствие доступного
соответствия в проверенном upstream endpoint, а не доказывает, что commit не
существует ни в одном fork. Проверка совместимости (`experiments/system-one-pilot/archive-compatibility.json`).

## 2. Разделение и проверяемая разметка

До извлечения train/dev observations закреплён групповой split:
**57 train / 20 dev / 20 test, 29 компонент**, seed 20261019. Используются явные
варианты шаблонов, конкретные общие entities из reference arguments и scenario
5-gram Jaccard ≥0.55. Общий tool/policy сам по себе не образует группу.
Все производные chunks наследуют task family/split; ни одной test-строки и ни
одного exact input overlap train/dev в итоговой очереди нет.
Split manifest (`experiments/system-one-pilot/manifests-v3/split.json`),
аудит утечек (`experiments/system-one-pilot/leak-report.json`).

Сохранены два отклонённых разбиения: ошибка tool-name-as-entity дала одну группу;
после её исправления audit ancestry объединил близкие cash-back варианты.
Окончательный split закреплён **до меток, inference и CE**. Технические длины
входов изучались на train/dev отклонённого split; pristine blind-test не заявлен.
Исходные задачи ранее изучались в проекте, сам benchmark публичный. Модельные
метрики/метки окончательных test ID не получались и для настройки не использовались.
Идентичность архивных task IDs текущим задачам остаётся отдельным блокером, поэтому
этот архивный опыт не доказывает корректность независимого task-held-out сравнения.

Рубрика `usefulness-v1`: useful — фрагмент даёт правило, исключение, факт или
диагностический шаг, применимый к **наблюдаемой** текущей потребности; irrelevant —
другая операция/известный другой продукт либо нет полезного правила; uncertain —
неизвестное предусловие, тип карты или недостаточный обрывок. Например, при
неизвестном типе карты специфичный referral threshold отмечен uncertain, а не 0.
Оценка отдельного фрагмента не является меткой достаточности всего набора.

Разметчик — один Codex-агент в текущей сессии, точный serving model ID недоступен.
Нет второго независимого читателя, disagreement rate и adjudication. Метки
**предварительные**, не validated gold. Required_documents и будущий reward
не использовались как метки. Цитаты, input hashes, исходный event, причины и статус
machine review сохранены в annotations-v1.jsonl (`experiments/system-one-pilot/annotations-v1.jsonl`).
Локальная HTML-форма `artifacts/system-one-pilot/annotation-review.html` показывает
каждый вход для ручной проверки. Синтетические контакты и тела наблюдений в Git
не включены; исходная лицензия архивных trajectories отдельно не подтверждена.

Выбор до прогнозов: round-robin по task IDs/row hashes до 64 admitted train,
все 27 admitted dev. Итог — **91 пара**: train 11 useful / 37 irrelevant /
16 uncertain; dev 8 useful / 19 irrelevant. CE получает **48 hard train-пар**
из 7 задач / 5 групп; dev — **27 пар одной задачи task_023 / одной группы**.
Unknown не превращается в отрицательную цель. Отбор по admission создаёт смещение:
короткие хвосты длинных документов проходят чаще; 91 строка не равна 91 задаче.

## 5. Расходы, ошибки и хранение

Новые inference API **$0**, аренда GPU **0 ₽**, платных вызовов нет. HTTP-загрузка
публичных файлов не требует платного inference сервиса. Электроэнергия, время
человека/агента, стоимость текущей Codex-сессии и исходной генерации архива не
измерены; полная стоимость исследования не равна нулю. Стоимость полного
agent service, simulator/judge, fallback и окупаемость пока неизвестна.

Сохранены DNS failure sandbox, HTTP timeout архива с дозагрузкой хвоста и проверкой
целого SHA, несовместимая tokenizer config, ошибочный split, ancestry/preprocessing
revisions, HTTP404/422, результаты review и посторонний тест презентаций.
Реестр ошибок (`experiments/system-one-pilot/errors.json`).
Review воспроизвёл превращение `null` в negative и отсутствие hash source Laya;
добавлены regression tests, строгие labels и фактические hashes. Реальная первая
разметка null не содержала, поэтому её метрики этим дефектом не испорчены.

Raw bodies, source archive, snapshot queue, исходные weights и обе adapted heads
остаются локально; в Git — разрешённые metadata, labels без тел входов, события и
отчёт. Каталог и контрольные суммы (`experiments/system-one-pilot/artifact-manifest.json`).
Игнорируемые файлы не являются резервной копией; новое общее хранилище не выбрано.
Код и предварительная разметка выполнены Codex по поручению инициатора;
человеческая проверка меток и научное авторство этим не приписаны участникам.

Проверки завершения: **11/11 тестов пилота**, повторное построение queue/snapshots
с идентичными SHA, валидация всех 91 annotations, сверка checkpoint и raw results;
GitMark strict lint/index, MkDocs strict build в `site/`, `git diff --check`.
Общий unittest suite: **41/42**, одно существующее падение презентаций из-за
уже имевшегося второго PPTX; чужой файл не удалялся. Независимый агент провёл
read-only review и повторную проверку исправлений: новых Critical/Important нет.

## 6. Следующий эксперимент и устранение препятствий

**Решение по этому пилоту:** CE технически работает, но текущий replay не принимать
как подтверждение полезной доменной адаптации. Не увеличивать training budget и
не переходить к RLCD; сначала исправить данные.

**Уточнение 24.10.2026:** инициатор выбрал следующий сбор из полных диалогов;
решение и объём технического старта — в вопросе
[«С каких диалогов начать новый сбор данных?»](README.md#wayfinder-dialogue-collection).
Описанный ниже first-turn-only путь сохранён как прежнее предложение 19.10.2026.
Требования к проверке происхождения, рубрики, admission и независимости групп
сохраняются; модели и бюджет нового сбора ещё обсуждаются.

Прежнее предложение следующего опыта — first-turn **retrieval-only probe** текущего pinned
banking KB: зафиксировать по одной видимой пользовательской реплике минимум для
8 train и 6 dev **разных групп**, выполнить локальный native BM25 с query равным
этой реплике и top-k10, сохранить настоящий tool output и snapshot. Реплики
создать и проверить как отдельные scripted-user fixtures, наследующие sealed
task family; не извлекать hidden Task в scorer. Это бесплатный способ проверить
admission/рубрику, но он ещё не full-agent оценка. Этот collector пока не реализован:
его контракт и целевой результат указаны здесь, исполняемая команда не выдумана.

Сначала независимо разметить двумя читателями небольшой train audit, например
20 пар с положительными, hard negative и uncertain, сохранить disagreement и
adjudication; затем заморозить рубрику до dev. Получить несколько dev-групп с
обоими hard-классами и опубликовать admission по всему пулу. После этого повторить
один CE-vs-frozen-vs-BM25 опыт с тем же бюджетом, group-macro метриками и честным
охватом. Проверять 1024 до расширения окна, чтобы не ввести новый фактор сразу.

Для требуемых полных native эпизодов есть два конкретных пути: предоставить
локальный OpenAI-совместимый actor/simulator/judge с закреплёнными версиями и
запустить штатный evaluator; либо заранее определить provider/model, estimate,
численный API hard limit и stop rule, получить разрешение и только затем собрать
эпизоды на pinned bm25. **30 000 ₽ планового GPU-резерва не являются разрешением.**
Архив можно использовать для основной серии только после получения исходного
task bundle/KB и подтверждения соответствия IDs/ancestry; одного совпадения имён
недостаточно. Test остаётся вне разметки для разработки, HPO и выбора порогов.

## 7. API-профиль нового сбора — 24.10.2026

**Согласовано инициатором:** использовать API и DeepSeek в обеих ролях;
**общий лимит первого технического сбора — $1**, включая smoke-test и повторы.
Конкретный snapshot — `deepseek/deepseek-v4.1-flash-1017` через
OpenRouter. Предлагаемые настройки: закрепить провайдера DeepSeek без
автоматической смены провайдера; роль агента — reasoning low,
роль симулятора — без reasoning.
Сценарии, промпты и доступ к данным у ролей разные. Совместимость параметров и
поведение симулятора требуют smoke-test; утверждения о качестве в banking нет.
Выбор двух разных LLM для разметки на 24.10.2026 оставался отдельным решением;
25.10.2026 он принят в [профиле разметки](#annotation-model-proposal).

Проверены публичные источники 24.10.2026:
[каталог OpenRouter](https://openrouter.ai/api/v1/models),
[endpoint карточка snapshot](https://openrouter.ai/api/v1/models/deepseek/deepseek-v4.1-flash-1017/endpoints),
[тариф DeepSeek](https://api-docs.deepseek.com/quick_start/pricing/),
[закрепление провайдера](https://openrouter.ai/docs/guides/routing/provider-selection).
В каталоге snapshot указан с input $0.15/M и output $0.60/M вне peak;
для расчёта ниже консервативно взяты peak $0.30/M и $1.20/M соответственно.
Перед исполнением тариф выбранного endpoint проверяется повторно.

**Фактическое исполнение 25.10:** после двух HTTP404 из-за account training
policy инициатор отдельно разрешил `deepinfra/fp8` для сбора и DeepSeek-разметчика.
Модель та же, privacy-настройки сохранены, fallback выключен. Исходное предложение
официального provider выше заменено этим решением; [измерения и расходы](#api-implementation-v1).

**Сценарная арифметика, не измеренный прогноз:** на один эпизод суммарно у агента
и симулятора 0.2–1.0 млн входных и 10–50 тыс. выходных токенов, включая reasoning.
Вход учитывает повторную передачу накопленной истории на каждом вызове.
Без скидок кеша это $0.072–0.36 за эпизод: 3 эпизода — $0.216–1.08;
5 — $0.36–1.80. При других длинах или повторах сумма меняется.
LLM-разметка в оценку не включена; используется native BM25 без embedding API.

Первоначальное предложение агента о лимите $3 **заменено решением инициатора
о лимите $1**. Цель — 3–5 эпизодов в пределах этого лимита; количество завершённых
эпизодов не гарантируется скидкой кеша. Перед каждым вызовом проверять бюджет
с резервом под полный некешированный input и разрешённый максимум output;
при нехватке остатка остановить сбор, не повышать лимит и не перезапускать серию
автоматически. Нужны численные ограничения шагов, токенов и повторов и учёт usage.
Разметка двумя LLM не входит в разрешённый бюджет сбора. Ключ добавлен
25.10.2026; [актуальный статус исполнения](#api-implementation-v1).

**Кеш:** у официального DeepSeek автоматическое серверное кеширование общих
префиксов; отдельное клиентское хранилище или `cache_control` для него не нужны.
Клиент продолжает передавать полный разрешённый контекст; стабильные инструкции,
порядок tools и уже отправленные сообщения не переставляются ради каждого шага.
Новые сообщения добавляются в конец; роли сохраняют раздельные истории и права
видимости. Кеш не является сохранённым ответом, не освобождает контекстное окно
и не отменяет стоимость генерации. Попадания best-effort, а не гарантированные.
Фактические cached tokens и стоимость сохранять из usage OpenRouter.

[DeepSeek Context Caching](https://api-docs.deepseek.com/guides/kv_cache/),

## 9. План проверки длинных входов Laya — 25.10.2026

**Проверенные факты:** у локального multilingual checkpoint `max_len=1024`,
`head_max_len=256`; у его encoder `max_position_embeddings=8192`. Текущая
[карточка автора](https://huggingface.co/convaiinnovations/laya-multilingual)
описывает явный `max_len` до 8192, отдельно предупреждая о проверке качества
длинных входов. Возможность настройки не является нашим измерением качества,
памяти или времени на 4k/8k. Старый архивный профиль принял 183 из 783 пар при
1024; это не прогноз покрытия нового BM25-сбора.

**План согласован инициатором 25.10.2026:** проверить профиль 4096, разбивать
длинные документы и учитывать отказы отдельно. Новых измерений пока нет.
На новых train-наблюдениях сначала
измерить длины полного сериализованного входа для лимитов 1024/4096/8192;
4096 рассмотреть как первый рабочий профиль после локальной runtime-проверки.
Измерения длины не требуют inference API. До выбора основного профиля проверить
входы и predictions на доступной проверенной train-подвыборке, время и память;
зафиксировать один профиль для frozen/adapted. 1024 сохранить как исходную
точку, 8192 — кандидат для отдельной проверки, а не автоматический оптимум.

Длинный документ разбивать по заголовкам/абзацам с сохранением преамбулы,
условий, source spans и версий; короткую запись оставлять целиком. Считается
state + кандидат + инструкции/варианты/оформление и внутренние head limits,
не одна длина фрагмента. Один oversized неделимый блок — `CANDIDATE_OVERFLOW`.
Если обязательное состояние само не помещается — `STATE_OVERFLOW`; разбиение KB
это не исправляет. Тихая truncation, удаление старых условий и подстановка
LLM-сводки не входят в согласованную базовую серию.

Непригодные пары и снимки сохраняются с причинами; их не превращают в negative
labels и не вычёркивают из отчёта охвата. Offline метрики на admitted-подмножестве
явно условные. В будущем online опыте техническая передача всего того же snapshot
LLM требует учёта стоимости и пригодности входа; native baseline при этом
остаётся самостоятельным неизменным контролем. Эта ветвь описана в
[контракте переполнений](architecture.md#context-contract-v0), не реализована
и не запускается в текущем сборе исходных диалогов.

Сканирование длинного входа окнами (`predict_long`) есть в закреплённом коде
Laya, но его агрегация не гарантирует совместного учёта условия и исключения
из разных окон. Для текущего плана это отдельный возможный метод,
не незаметная замена pointwise-входа и не выбранный fallback.

<a id="trusted-annotation-policy"></a>

## 11. Доверенная разметка DeepSeek + Qwen3.8 — 25.10.2026

**Действующее решение инициатора после просмотра ответов:** доверить всю разметку
связке DeepSeek + Qwen3.8. Агент сам разрешает рядовые расхождения, ошибки формата,
дефекты и неопределённости. Обращаться к инициатору **только при критическом
противоречии, которое агент не может разрешить сам**. Это заменяет прежнюю
обязательную ручную очередь, случайные слепые контроли и human audit как gate.
Не возвращать их в следующих сериях без нового поручения. Выбор моделей,
информационные границы, отдельные бюджеты и правила учёта остаются прежними.

Политика `deepseek-qwen-agent-v1`:

- Полные валидные ответы обеих моделей совпадают и не указывают дефект — принять
  автоматически, включая законную `uncertain` (без бинарной training-метки).
- Расхождение/technical error/defect — сначала разбирает агент по тому же
  state+candidate, рубрике и происхождению. Его решение отдельно сохраняет
  основание и точные цитаты; исходные ответы не переписываются. Ошибка JSON/цитаты
  не превращается в семантическую uncertain и не считается вторым валидным ответом.
- Неизвестная применимость сама по себе разрешима как uncertain. Критическое
  противоречие — существенная несовместимость фактов/правил либо нарушение
  информационных границ/происхождения, которое нельзя разрешить по доступным

### Решение о RLCD

**Рабочее решение: пока не запускать RLCD.** CE/Brier улучшили согласие узла
с метками относительно frozen, но не превзошли дешёвый train-prior по
accuracy/Brier/NLL и не увеличили число подтверждённых успехов полного агента.
Три семейства, пять useful validation примеров, четыре технических отказа и
единственная общая полностью оценённая задача не дают основания выбирать
более дорогой метод обучения. Это не эксперимент, доказывающий неэффективность RL.

Следующие предложения — отдельный заранее закреплённый опыт с переиспользованием
encoder prefix/батчированием, простым calibration/threshold контролем и более
надёжным native tool-call output, затем расширение независимой проверки.
Они этой серией не запускались. Финальная test-выборка остаётся нетронутой;
выбор основного метода/формулировки ВКР этим техническим пилотом не утверждается.
