# Атлас исследования — адаптация System One на τ-bench

Подготовлено **19.10.2026** по поручению инициатора. Это подробный проект исследования
и навигация по его реализации. Обучение, новые агентные прогоны и измерение качества
этим документом **не выполнялись**. Численные объёмы и сроки ниже — стартовые
предложения, которые проверяются пилотом. Поддержку направления руководителем
не следует трактовать как утверждение этой матрицы опытов.

**Рабочая тема:** «Влияние доменной адаптации компактной модели вероятностного
отбора контекста на качество, стоимость и задержку языкового агента».

**Основной вопрос:** улучшает ли дообучение System One на наблюдениях из обучающей
части `banking_knowledge` соотношение качества и полной стоимости по сравнению
с той же моделью без адаптации и LLM-селектором на независимых задачах той же области?

## Что зафиксировано и что предлагается

**Поручение 19.10.2026:** сравнить LLM baseline, default System One и дообученную
System One; данные адаптации получать из той же области τ-bench. Рассмотреть
влияние функции обучения и рассуждений. Нужны общий и подробные планы, roadmap,
архитектура, сбор данных, протокол измерений и анимированные иллюстрации.

**Ранее принятая граница:** System One выбирает контекст из накопленного пула
KB-наблюдений текущего диалога. Один основной LLM-агент формирует ответы и tool calls.
Native policy, задачи, tools и evaluator сохраняются. Три направления команды —
маршрутизация, отбор и адаптация; личный вклад инициатора — адаптация.
См. [каноническую постановку](research.md#постановка-и-границы) и
[контракт v0](architecture.md#context-contract-v0).

**Предложение атласа:** минимальный обязательный опыт — frozen против adapted
одной компактной модели при фиксированных входе, packer и actor; LLM-селектор
и дешёвые контроли показывают практическую ценность. CE/Brier — первая абляция.
Рассуждения учителя и RLCD добавляются только после рабочего базового сравнения.
При этом OpenJev-RLCD генерирует rationale, а Laya/SBERT2S1-RLCD использует
возмущения logits без генерации текста; эти рецепты не взаимозаменяемы.
Выбор весов, split IDs, расходный лимит API, гиперпараметры и допустимая потеря
качества ещё не закреплены.

## Формальная схема

В момент t наблюдаемая история Hₜ преобразуется фиксированным правилом в состояние
sₜ. Пул Dₜ содержит только реально полученные к этому моменту KB-единицы.
Компактный оценщик Cθ выдаёт для каждой пары (sₜ, dᵢ) значение pᵢ в [0, 1].
Метка yᵢ означает заранее определённую полезность фрагмента для текущей
информационной потребности; это не вероятность успеха всего диалога.

Детерминированный packer P выбирает Sₜ = P(Dₜ, p, Bₜ). Производный вход основного
агента содержит защищённую историю, неизменную policy/tools и один блок Sₜ.
Решение и новый tool result меняют следующий snapshot; цикл продолжается до native
завершения. На одном offline snapshot сравнивается качество оценщиков; в online
прогонах история разных агентов может разойтись. Эти два типа эксперимента
отвечают на разные вопросы и не заменяют друг друга.

Для бинарного полезен/неполезен:

- CE: −mean[y log p + (1−y) log(1−p)].
- Binary Brier: mean[(p−y)²]. Векторный Brier по двум классам вдвое больше;
  соглашение фиксируется в метриках.
- Цель deployment: уменьшить E[C_episode] при ограничении на потерю Q_episode
  относительно выбранного baseline; L_episode публикуется отдельно.

Proper loss не гарантирует калибровку вне распределения обучения. Полезность
отдельных фрагментов не доказывает достаточность набора. Поэтому измеряются
полезность, полнота evidence set, native успех и полные расходы.

## Три главных сравнения и обязательные контроли

| ID | Что меняется | Что фиксируется | Какой вывод допустим |
| --- | --- | --- | --- |
| A — LLM selector | LLM совместно выбирает упорядоченный список IDs; результат проходит валидацию | Общие state/pool/budget, actor, seeds, policy/tools | Практическая цена генеративного отбора |
| B — S1 default | Исходные опубликованные веса compact scorer | Тот же packer и вход, что C | Точка отсчёта доменной адаптации; default уже предобучен |
| C — S1 adapted | Веса/адаптер обучены только на train | Всё кроме адаптации, одинаковая процедура dev selection | Добавочный эффект адаптации |
| N — native | Исходный агент без нашего selector harness | Native policy/tools/evaluator и версии actor | Исходный уровень качества и расходов |
| H — дешёвые | BM25 по observed_pool, recency, при возможности простой classifier | Общий packer/бюджет | Нужна ли вообще обучаемая модель |

Основной A выбирает список целиком, поэтому сравнение с B/C включает различие алгоритма отбора.
Для сравнения именно оценщиков добавить отдельную абляцию A-pointwise с тем же packer. Все arm
используют один основной actor, например закреплённый snapshot DeepSeek Flash.
Название модели, provider, режим reasoning, дата и возвращённый ID сохраняются;
плавающий API alias недостаточен. Наличие версии проверено в
[реестре источников](system-one-atlas-evidence.md).

Первый причинный опыт B↔C проводится без обучаемого маршрутизатора: семантическая
политика always_accept, одинаковый технический fallback. Технические отказы и его
стоимость остаются в метриках. R и подбор порогов — отдельный блок команды.
Штатную temperature исходной модели фиксировать как часть B-published. Чтобы
отделить адаптацию от новой калибровки, отдельно сравнить raw B/C и B+TS/C+TS
с одинаковой процедурой на общем отложенном calibration subset; calibration
не должна незаметно появляться только у C. Основной контраст выбирается до test.

## Гипотезы и опровержения

| Гипотеза | Проверка | Что опровергает или ограничивает её |
| --- | --- | --- |
| H1: адаптация повышает полезность compact scorer | B↔C на held-out snapshots, затем episodes | Улучшение только train; test CI не позволяет заключить о выигрыше |
| H2: Brier меняет качество вероятностей относительно CE | Один checkpoint, данные, budget, seeds; Brier/NLL и ranking | Эффект объясняется HPO, class balance или temperature scaling |
| H3: reasoning teacher даёт лучшие targets | Один учитель с/без reasoning; независимая проверка меток; student без rationale | Только согласие с учителем, без выигрыша проверенных меток/episode |
| H4: compact selector экономит | Полная стоимость против A и N/H | Время и цена scorer/fallback выше экономии actor/context |
| H5: качество сохраняется в допустимом диапазоне | Парная разность Q и заранее выбранная граница δ | Нижняя граница CI ниже −δ или слишком широкий CI |

Статистическая неопределённость — самостоятельный вывод. «Значимого различия
не найдено» не означает эквивалентность; критерий non-inferiority и δ задаются
до final test. Если эффект не отделим при доступных данных, это ограничение
исследования, а не разрешение расширять поиск по тесту.

## Предлагаемый roadmap

Отсчёт от фактического начала S, без выдуманной даты защиты. Один автор адаптации
работает совместно с владельцами общей платформы. Диапазоны ориентировочные,
разметка и runtime могут менять длительность. В интерфейсе roadmap можно задать
свою дату начала; это локальный сценарий планирования, не изменение wiki.
Перекрывающиеся недели допускают параллельную подготовку; зависимый запуск
ждёт входного артефакта и критерия готовности. При их задержке календарь сдвигается,
а границы test и проверки не сокращаются ради исходной даты.

| Недели от S | Основная работа | Проверяемый рубеж |
| --- | --- | --- |
| 1–2 | P0, P1 | Контракт и техническая выполнимость |
| 2–4 | P2, параллельно P3 | Harness и запечатанный split |
| 4–6 | P4 | Первый train/dev corpus с provenance |
| 6–8 | P5, начало P6 | Dataset v1, цена разметки, baseline |
| 8–11 | P7: сначала CE, затем Brier | Frozen↔adapted на dev |
| 11–13 | P7: teacher reasoning — только если базовый опыт готов | Небольшая дополнительная абляция |
| 14–16 | P8 | Замороженный final test и отчёт |
| 16–18 | P9 | Устойчивость, стоимость адаптации и окупаемость |
| 18–22 | P10 | Текст, приложение, воспроизведение и защита |
| 23–24 | Резерв | Исправления проверок, без скрытого подбора по test |

Написание постановки, обзора и методики идёт с первой недели. RLCD не находится
на критическом пути: если не помещается по данным, ресурсам или срокам,
он остаётся рассмотренной научной перспективой с точным основанием отказа.

## Ресурсы и условия остановки

Доступные ресурсы и их статус — в [ресурсной оценке](resource-assessment.md).
Основная рабочая машина — Mac M4 Pro / 24 ГБ; GPU rental до 30 000 ₽. Это потолок
планирования, не разрешение начинать платную серию. Лимит API ещё не установлен.

Предложение распределить GPU-резерв: 20% на профилирование и первый CE пилот,
45% на основное сравнение CE/Brier, 15% на повторения и 20% на резерв. Доли
пересматриваются по измеренной цене часа и времени шага. Стоимость учителя,
simulator и evaluator оценивается отдельно и может доминировать над training.

До платной серии требуется run estimate с числом задач, повторов, средним/верхним
потреблением, стоимостью токенов и GPU, жёстким лимитом и остановкой при его
достижении. Ранее согласованное разрешение используется без повторного запроса.
Сейчас артефакты только описывают эти будущие действия.

Сначала проверить 50–100 train-пар и малый batch на доступном устройстве;
дальше — pilot subset train/dev. Объёмы являются предложениями, не обещанием
достаточности. Проверить память, latency, backward/update и полезность gradient
до планирования большой серии. Нет рабочего пути обучения выбранной модели —
сменить compact checkpoint с записью причины, а не объявлять новый classifier
«дообученной той же моделью».

## Как строить выводы

1. Сначала подтвердить валидность данных и сравнения: split, labels, общий вход,
   версии, учёт fallback и ошибок. При нарушении исправить протокол новым прогоном.
2. Сопоставить B и C: как изменились вероятности и отбор; объяснить, перешёл ли
   эффект в native успех. Не подменять одно другим.
3. Сопоставить C с A, N и H: оправдана ли сложность и сколько стоит полный эпизод.
4. Проверить стоимость адаптации. Если допустимость потери качества подтверждена
   и экономия на эпизод положительна,
   `N* = C_adaptation / (C_reference − C_adapted)`; если неположительна,
   конечной окупаемости нет. Диапазон `N*` должен учитывать неопределённость.
5. Разделить локальный вывод по этому домену, возможный механизм и непроверенное
   обобщение на другие домены. Same-domain split не доказывает перенос в другой банк.
6. Описать собственный вклад: dataset design/labels, обучение, абляции, измерения,
   анализ. Общий harness и работа других участников обозначаются явно.

ВКР может быть завершена при любом знаке эффекта, если выполнены постановка,
воспроизводимый агент, корректные измерения и сравнение. Итоговая карта связывает
«вопрос → данные → метод → опыт → измерение → вывод», а не заранее заданного победителя.

## Как пересобрать и проверить сам атлас

Содержательный текст хранится в пяти документах `docs/gitmark/system-one-atlas*.md`.
Данные схем — в `scripts/research_atlas_data.py`, генератор —
`scripts/build_research_atlas.py`, локальная копия MIT-шаблона
architecture-diagram v1.4.0 — в `scripts/templates/research_atlas.html`.
HTML в `docs/research-atlas/` и `site/research-atlas/` — производные представления.

Реальные команды сборки документации из корня репозитория:

```sh
.venv/bin/python scripts/build_research_atlas.py
python3 .claude/skills/kb-search/gitmark.py lint --strict
python3 .claude/skills/kb-search/gitmark.py index
.venv/bin/mkdocs build --strict
.venv/bin/python scripts/check_site.py
```

Для браузерной проверки предназначен `scripts/check_research_atlas.cjs`:
нужны Node.js, установленный Playwright и локальный Chrome. Скрипт использует
пакет через стандартный `NODE_PATH`, при ином расположении браузера — `CHROME_PATH`.
Он открывает только локальные страницы и блокирует HTTP(S), проверяет сценарии,
каждый шаг, пуск/паузу, тему, узкий экран, roadmap, матрицу обучения, калькулятор
и reduced motion. Снимки и `report.json` пишет в игнорируемый
`artifacts/research-atlas-check/`. Модельные эксперименты эти команды не запускают.

Для показа открыть `site/research-atlas/index.html` или обслуживать `site/`
локальным HTTP-сервером. Каждый файл содержит собственные CSS, JavaScript
и подробный текст; для переходов к соседним страницам нужен весь каталог сайта.
Изменение даты/ползунка roadmap — просмотр сценария, не запись фактического прогресса.

Проверка артефактов 19.10.2026: 21 HTML-страница, 48 сценариев и 183 перехода
пройдены в локальном Chrome без ошибок JavaScript, предупреждений браузера и
сетевых запросов. Проверены 610 локальных ссылок/якорей, desktop и ширина 390 px,
переключатели, roadmap, калькулятор и reduced motion. GitMark strict, MkDocs strict
и сверка производного `site/` прошли. Это результаты проверки документации,
не измерения исследовательских моделей.
