# Задачи проекта

Канонический список задач — [«Ближайшие задачи»](../README.md#ближайшие-задачи).
Отдельный трекер сейчас не используется.

- Новую задачу добавлять в этот список. При детализации указывать ответственного,
  проверяемый результат и ссылку на проверку согласно [правилам wiki](../README.md#правила-ведения-wiki).
- Статус триажа при необходимости указывать рядом с задачей по
  [словарю статусов](triage-labels.md). Не добавлять статусы задним числом без нужды.
- PRD и подробную постановку размещать в подходящем каноническом документе
  и связывать с пунктом списка; не создавать параллельную копию списка задач.
- Для поиска задачи читать пункт списка и связанные документы.

## Wayfinding operations

Для `/wayfinder` используется тот же локальный Markdown-трекер: карта и её
дочерние вопросы — отдельные именованные записи в разделе «Ближайшие задачи».
Новый параллельный реестр и внешняя публикация не требуются.

- Идентичность записи: стабильный `ID` и явный HTML-якорь; название может меняться.
  Человеческие ссылки оформлять названием, а не голым ID.
- Метаданные карты: `Label: wayfinder:map`, `Status: open/closed`, ведущий.
  Тело — Destination, Notes, Decisions so far, Not yet specified, Out of scope.
- Метаданные вопроса: `Label: wayfinder:grilling/research/prototype/task`,
  `Parent`, `Status`, `Assignee`, `Blocked by`. Тело — Question; это решение,
  не задача реализации. Триажные labels к wayfinder-записям не добавлять.
- Сначала создать все записи с реальными ID/якорями, затем добавить ссылки Parent
  и Blocked by. Нативных dependencies у Markdown нет: поле Blocked by —
  каноническая связь, содержащая ссылки на блокирующие вопросы.
- Найти frontier: среди записей нужного Parent выбрать `Status: open`,
  `Assignee: unassigned`, у которых все Blocked by закрыты; порядок — по документу.
  Открытые вопросы не копировать в тело карты отдельным списком.
- Claim: перед работой перечитать запись и назначить в Assignee ведущего
  разработчика/инициатора. При параллельной работе согласовать запись до правки;
  файловый трекер не предоставляет атомарной блокировки.
- Resolution: после решения добавить к записи отдельный подраздел
  `Resolution comment — <дата>` с ответом и источником согласования, поставить
  `Status: closed`; в Decisions so far карты добавить только краткий итог
  со ссылкой на вопрос. Вопрос сохраняется, ответ не вписывается вместо него.
- При charting все новые вопросы остаются открытыми; согласованные до карты
  границы находятся в канонической постановке и доступны из Notes. При работе
  по карте закрывать не более одного нересёрч-вопроса за сессию. HITL-вопрос
  закрывается только после живого ответа пользователя.
- Новое исследование вне репозитория оформлять отдельным research-вопросом
  по мере необходимости. Локально уже проверенные факты связывать с вопросом;
  повторное внешнее исследование ради заполнения карты не запускать.
