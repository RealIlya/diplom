# Полные вызовы инструментов без LLM на каждом шаге

**Статус: проработка вариантов 11.10.2026, не принятая реализация.** Пользователь
попросил развивать второй путь — полный tool call без генеративной LLM на
автоматизированном шаге. Name-only selector с последующей генерацией аргументов
сохраняется как контроль, не основной механизм сокращения числа LLM-вызовов.
[Вопрос карты](README.md#wayfinder-decision-contract) остаётся открытым.

Это уточнение [общей схемы-кандидата](architecture.md#shared-integration-proposal),
а не новый benchmark или обещание автоматизировать весь диалог. Ни модельные
прогоны, ни оценка покрытия/экономии, ни обучение здесь не выполнялись.

## 1. Главная рекомендация

Начать с **выбора небольшого набора полностью сформированных вызовов (A)**.
Когда нужный аргумент неоднозначен, расширять его **выбором значения из наблюдаемых
кандидатов (B)**. После каждого tool result снова принимать решение; несколько
таких шагов подряд могут обходиться без LLM и без заранее написанной процедуры.

**Процедуры (C)** — последующее расширение, если независимый выбор слишком
дорог или нестабилен. **LLM-план с локальным исполнителем (D)** — отдельная
альтернатива для сложных многошаговых задач, а не обязательный supervisor
на каждом шаге. A/B задают способ построения вызова, C/D — управление
последовательностью; они могут сочетаться, а не образуют четыре взаимоисключающие
архитектуры. Это рекомендация для обсуждения, не выбранный пользователем вариант.

Граница автоматизированного шага: **ноль генеративных agent-вызовов для его
подготовки, выбора, заполнения аргументов и проверки**. Если дорогая модель
сначала составляет кандидаты или сводку заново на каждом шаге, заявленного
механизма сокращения вызовов нет. В D планирование — отдельный оплаченный
LLM-шаг; лишь последующие шаги исполнения могут считаться автоматизированными.

## 2. Общий контракт

Наблюдаемая история h порождает разрешённые факты F(h), видимые описания tools
и конечный набор кандидатов C(h). Один кандидат содержит:

- имя native tool и полный словарь его аргументов;
- для discoverable операции — конкретное найденное имя, успешный unlock
  и сериализованные внутренние аргументы;
- ссылки на наблюдения, откуда взяты значения и условия применимости;
- версию состояния, чтобы старый результат не использовался после изменения
  пользователем цели, объекта или подтверждения.

Модель выбирает кандидата, а политика маршрутизации решает принять его или
передать **всё решение** LLM. Возможность `defer` обязательна; пустой/непокрываемый
набор сразу передаётся LLM и не требует бессмысленного scorer-вызова.

~~~text
наблюдения → факты и разрешённые схемы → полные кандидаты
          → KEV/Laya: выбор и оценки
          → калиброванная политика + проверяемые предусловия
              accept: точная сериализация → AssistantMessage → native tool
              defer: native LLM выбирает действие и аргументы/реплику
          → новый результат → заново построить кандидаты
~~~

JSON строит обычный код, не модель. Код обеспечивает соответствие схеме,
копирование значений и известные ограничения, но не гарантирует правильность
намерения или соблюдение всех естественно-языковых правил. Неразрешённая
семантическая неоднозначность не объявляется «проверенным policy flag».

Softmax по кандидатам не измеряет автоматически корректность полного вызова:
при единственном варианте p=1 даже у ошибочного действия, а при отсутствии
правильного варианта распределение всё равно нормировано. `defer` не исправляет
это сам по себе; нужны метки полного вызова и независимая калибровка.

**Это не скрытая генерация произвольного JSON.** Новая сумма, формулировка
объяснения, свободный поисковый запрос и значения, которых нет среди доступных
вариантов, требуют отдельного способа получения либо fallback.

### Что уточнила проверка реальных banking tools

[Первичный аудит native вызовов](complete-call-native-audit.md) проверил commit
`4ce7c0397c1eb65c9bbe59aeacfe1ca44a1cd699`, без запуска среды и чтения test-задач.

1. Обычные read tools возвращают **текст** `Record ID` / `field: value`,
   а не schema-guaranteed JSON. Нужен версионированный parser наблюдений,
   сохраняющий исходное сообщение и неоднозначности. Ошибка разбора — `defer`,
   не восстановление поля из БД. Ключ записи, business user_id и document ID
   не взаимозаменяемы; наличие нужного поля проверяется в полученном тексте.
2. Для персональных данных policy требует два верно названных пользователем
   identity-фактора и запись `log_verification`. Запись — WRITE с семью
   обязательными строковыми аргументами, а не endpoint проверки личности.
   Успешное логирование само не доказывает совпадение факторов. Время берётся
   из `get_current_time`, не из константы исходника или системных часов harness.
3. Точный bootstrap lookup до верификации формально не описан policy.
   Неоднозначную начальную идентификацию и её логирование в первом пилоте
   предлагается оставить штатной LLM; fast path обычных персональных reads
   начинается **после** их корректного исполнения. Эпизод в целом не read-only.
4. Unlock меняет внутреннее состояние, а вызов discoverable read через wrapper
   может писать служебную DB. Нельзя считать их чистыми чтениями, пропускать
   логируемые шаги или пользоваться внутренним allowlist оценивания.

**Иллюстрация, не benchmark-задача:** `U` — значение user_id из реально
наблюдавшегося результата, связанное с проверенным клиентом; идентификация,
логирование и прочие предпосылки уже выполнены. Тогда синтаксически полные
кандидаты можно представить так:

~~~json
[
  {"name": "get_credit_card_transactions_by_user", "arguments": {"user_id": "U"}},
  {"name": "get_credit_card_accounts_by_user", "arguments": {"user_id": "U"}},
  {"name": "get_referrals_by_user", "arguments": {"user_id": "U"}}
]
~~~

В реальном вызове строка `U` заменяется наблюдённым значением, не шаблоном.
Смысловой выбор зависит от текущего запроса; список не означает разрешение
выполнить всё, наличие всех предусловий или доказанную потребность в нейросети.
Технические ID/requestor добавляет адаптер. Конкретные сигнатуры и ограничения
возврата приведены в [таблице первичного аудита](complete-call-native-audit.md#2-шесть-обычных-read-tools).

## 3. A — выбор полного вызова из наблюдаемых кандидатов

**Как работает.** Существующие схемы и данные наблюдений дают готовые к
сериализации варианты. Простой пример типа связывания: инструмент принимает
идентификатор клиента, а этот идентификатор уже присутствует в разрешённом
ответе поиска клиента. Создать полный словарь аргументов можно без LLM.
Один и тот же идентификатор может подходить нескольким разным операциям;
смысловой выбор остаётся за компактной моделью.

Другие источники кандидатов: точное копирование явно названного значения,
объекты из наблюдаемого списка, enum из реально полученной схемы. Новые
значения не придумываются, hidden DB не читается.

**Выход:** ID одного полного вызова. Обычно один логический choice-запрос,
если весь набор и состояние помещаются; это не гарантия одного физического
forward для любого runtime/формата.

**Что экономит:** принятый вызов не требует LLM для выбора имени или аргументов.
Несколько принятых итераций могут сократить число генеративных запросов; факт
сокращения устанавливается по полным траекториям, с учётом native multi-call.

**Ограничения:**

- Для нескольких полей декартово произведение значений быстро разрастается.
  Совместимые пары строятся по наблюдаемым связям, а не по совпадению строк.
- Если допустимого следующего вызова нет в C(h), никакое обучение selector
  не исправит это. Нужны candidate recall и fallback, не подмешивание gold.
- Если правила уже однозначно выбирают действие, модель может быть лишней.
  Нужен самостоятельный rule-only контроль, а не искусственно слабая заглушка.
- Получить объект недостаточно: он может относиться к другому обращению,
  а сведения — устареть после новой реплики.

**Пилот:** обычные инструменты чтения с уже наблюдёнными идентификаторами;
retrieval и discovery считать отдельными семействами, не автоматически
эквивалентными read-only банковским запросам. Политики идентификации сохраняются.
Это начальная проверка механики, не обещание достаточного охвата всего banking.

**Дальнейшая область:** после проверки можно обсуждать полные discoverable
и изменяющие состояние вызовы с тем же механизмом выбора. Для них отдельно
определяются наблюдаемые предусловия, актуальность подтверждений и цена ошибок;
высокая уверенность не заменяет ни одно из условий. Это не запрет всех write-calls
навсегда, но и не разрешение автоматически включить их в первый пилот.

## 4. B — выбор операции и значений аргументов по частям

**Как работает.** Компактная модель выбирает операцию, затем значения из
допустимых наборов: какой наблюдаемый клиент/счёт/транзакция, какой enum,
какой заранее извлечённый фрагмент. Последующие наборы зависят от предыдущего
выбора; serializer собирает полный вызов только после всех обязательных полей.

Это отличается от первого пути пользователя: **аргументы тоже выбираются без
генеративной LLM**, а не передаются ей после выбора tool name.

**Выход:** составной выбор, заканчивающийся полным вызовом; ориентировочно
один запрос на операцию плюс запросы по неоднозначным полям. Независимые вопросы
иногда можно батчить; зависимые поля нельзя объявлять одним независимым проходом.
Можно сначала детерминированно связать очевидные поля и спрашивать модель
только о действительно неоднозначных значениях.

**Что экономит:** нет LLM-вызова для name/args, но появляется несколько
scorer-запросов. На длинном state повторный prefill может съесть выигрыш.

**Ограничения:**

- Ошибка раннего выбора меняет все последующие множества.
- Нельзя независимо выбрать user_id одного клиента и account_id другого.
  Нужны условные маски и наблюдаемые связи; полнота схемы этого не гарантирует.
- Произведение отдельных marginal probabilities полей не является joint
  distribution без обоснованной независимости. Настоящая условная факторизация
  может задать joint выбранной модели, но и оно не гарантирует эмпирической
  калибровки. Оценивать совместный результат и калибровать событие
  «полный вызов приемлем в этом наблюдаемом состоянии».
- Произвольный текст, не присутствующий среди кандидатов, остаётся за пределами
  такого интерфейса. Извлечение кандидатов само является частью метода.

**Роль:** точечное расширение A при множестве объектов, не обязательный
многопроходный маршрут для каждого простого вызова.

## 5. C — короткие процедуры с параметрами

**Как работает.** Повторяющийся участок работы представляется небольшой
процедурой с предусловиями, шагами, ветвлениями и точками остановки. System One
выбирает подходящую процедуру/следующий шаг и привязки аргументов; сами значения
берутся из наблюдений как в A/B. Процедуры выводятся из разрешённых общих правил
и development-материала, не из test reference actions.

**Что экономит:** процедура может выполнить несколько инструментальных шагов
без генеративного планирования между ними. При этом A тоже может выполнить
несколько шагов подряд: наличие процедуры само по себе не доказывает
дополнительного сокращения LLM-вызовов.

**Условия:**

- Каждый underlying tool call проходит native цикл, лимиты, checks и журнал.
  Нельзя превратить несколько действий в один невидимый среде «суперинструмент».
- Успех предыдущего шага и неизменность цели проверяются после каждого ответа.
  При неожиданном результате, новой инструкции пользователя или нехватке
  данных — остановка и пересборка/передача решения, не слепой replay.
- Заготовка процедуры не раскрывает каталог discoverable functions.
  Имена и параметры всё равно получаются штатным discovery в текущем эпизоде.
- Если план полностью описывается простым автоматом, сравнить этот автомат
  без модели. Модель оправдана только там, где остаётся содержательный выбор.

**Scorer-цена:** выбор процедуры — один вопрос; однозначный переход — ноль,
смысловое ветвление — один, плюс необходимые B-привязки. Если все переходы
однозначны, их исполнение — вклад автомата, а не модели System One.
Потолок корректной автоматизации задают покрытие библиотеки, доступные ветки
и полные bindings; fallback может расширить успех системы, но за свою цену.

**Риск:** дорогая ручная инженерия и узкий охват, перенос домена требует
нового протокола процедур. Не выбирать C первым только ради количества
автоматизированных строк кода.

## 6. D — LLM строит короткий план, System One исполняет

**Как работает.** LLM вызывается при входе в сложный участок и предлагает
ограниченный условный план: шаги, ссылки на будущие результаты, условия
выхода. Затем локальный исполнитель с A/B и System One выбирает переходы
и подставляет реально полученные значения. LLM возвращается при исключениях
или новом намерении, а не утверждает каждый следующий вызов.

**Что экономит:** один вызов планирования может заменить несколько последующих
вызовов генератора. Все planning/replanning-вызовы, токены плана и его проверки
включаются в стоимость. Если каждый ход требует нового плана или plan-validity
LLM, преимущество исчезает.

**Ограничения:** план с будущим transaction_id должен содержать ссылку на
ещё не полученное наблюдение, а не угаданный ID. Необнаруженная функция
не становится разрешённой от того, что LLM включила её в план. План — данные
ограниченного формата, не произвольный исполняемый Python/shell. После новых
наблюдений перепроверяются предусловия; длинные open-loop планы не нужны.

**Scorer-цена:** после отдельного генеративного planning/replanning — ноль
на однозначном переходе или один вопрос на смысловой выбор, плюс B-привязки.
Немодельная калибровка не требует нового backbone pass; дополнительный neural
validator требует. До перепланирования автоматизация ограничена ветками плана
и доступными bindings, а не всей выразительностью fallback LLM.

**Роль:** отдельное расширение после A/B; у него другая цена ошибок и больше
сложности. Нужен контроль «тот же LLM-план + детерминированный исполнитель»,
чтобы не приписать модели System One пользу самого плана.

## 7. KEV, Laya и контекст

- **KEV-4B:** кандидат для прямого выбора полного вызова A при достаточном
  ограниченном входе. Статистика When2Call не доказывает умение выбирать
  корректные аргументы; это новая проверяемая задача.
- **Laya multilingual:** альтернативный selector того же смыслового входа;
  длинное окно включается явно и проверяется целиком с вариантами.
- **Laya English/typed:** возможны для действительно короткого связывания
  или локального evidence scoring. Полную policy нельзя молча обрезать до
  512/1024; короткий вход должен сохранять все существенные для этого решения
  условия либо приводить к fallback.
- **KEV-0.8B:** не основной готовый router; возможен отдельный адаптационный
  или отрицательный контроль, а не обещание улучшить routing после обучения.

Ограничения и первичные карточки — в [аудите моделей](action-selection-review.md#8-ограничения-конкретных-моделей).
Для Laya длинные option descriptions могут обрезаться. Короткие ID вариантов
должны однозначно ссылаться на доступное модели полное описание кандидата;
прятать различия аргументов ради помещения в окно нельзя.

Отбор контекста должен сохранять не только тематическую релевантность документа,
но и условия действия, ссылки на связанные объекты и необходимые реплики.
Источник факта тоже существенен: значение из ответа инструмента не доказывает,
что пользователь сам правильно назвал это значение при проверке личности.
Сведения об идентификации и подтверждении нельзя получать из hidden state
или заменять необоснованным резюме. Построение view/summary также имеет цену;
LLM-summary на каждом ходе может вернуть все удалённые LLM-вызовы.

Нельзя спрятать выбор правильного действия в state builder: он предоставляет
факты, связи и ограничения, а не метку «следующая операция». Если semantic parser
или LLM уже решили, какой tool и какие аргументы нужны, сравнение исследует
другой узел; цену и ошибки такого решателя необходимо учитывать отдельно.

## 8. Как доказать, что LLM-вызовов действительно меньше

Считать **генеративные вызовы агента**, отдельно — scorer calls, user simulator,
evaluator и разовую подготовку данных. «Локальная LLM» всё равно является
генеративным вызовом; переименование её в helper не создаёт экономию.

Native LLM может одним сообщением выбрать несколько tools. Поэтому число
автоматически исполненных tools не равно числу удалённых LLM-вызовов.
Сравнивать фактические полные траектории на одинаковых задачах, а не объявлять
каждый fast-path tool сэкономленным вызовом. [Native контракт](action-selection-review.md#1-что-является-следующим-действием).

На одинаковом распределении задач измеряются:

- разность числа всех генеративных вызовов агента, включая planning, retries
  и fallback; не только успешные автоматизированные шаги;
- полная стоимость агента и на успешную задачу, setup отдельно;
- native pass^1 и интервалы разницы качества, policy/args/discovery ошибки;
- задержка p50/p95, длины входов, overflow, повторы поисков;
- доля состояний с полным candidate set, candidate recall по проверенным меткам,
  доля принятых решений и риск полного вызова среди принятых.

Локальный ориентир для A/B: ожидаемая цена пропущенной генерации должна
превышать цену построения кандидатов, scorers, контекста и последствий ошибок.
Это лишь диагностическое условие: новые траектории меняют количество шагов,
а сокращение числа вызовов не гарантирует сокращение токенов или денег.
Для D из выигрыша дополнительно вычитается planning/replanning.

**Минимальные контроли:** native joint LLM; тот же candidate builder и view
с простыми правилами; тот же набор с LLM-selector; KEV/Laya-selector с routing.
LLM на том же C(h) нужен для выделения эффекта селектора, native — для итоговой
пользы всей системы. Для нового контекста и factorized B — отдельные абляции,
не полный декартов перебор моделей. На принятом шаге A/B generator отсутствует.

## 9. Три самостоятельные работы на одном контракте

| Работа | Свой фактор | Что сравнивается |
| --- | --- | --- |
| Маршрутизация | Калибровка, accept/defer, цена ошибки | При одинаковых весах и view: правила/пороги, охват, риск полного вызова, итоговые расходы |
| Контекст | Отбор доказательств при бюджете | При фиксированной модели: recall условий/объектов, допустимость вызовов, качество против бюджета; простая релевантность не единственный критерий |
| Адаптация инициатора | Обучение и количество размеченных состояний | Один и тот же узел и архитектура: frozen против adapted, кривая обучения и перенос; RLCD-vs-без-RL — возможное последующее уточнение |

Candidate builder в опыте адаптации фиксируется. Если допустимого вызова нет
в наборе, усиление loss это не исправит. Для CE/Brier/RLCD нужны проверенные
приемлемые полные вызовы и явное правило target distribution при неоднозначности;
одна reference trajectory не предоставляет такую разметку автоматически.

Для честного RLCD-сравнения фиксируются исходные веса/backbone/head, данные,
view и настройка routing по одному протоколу. Готовая Laya против готовой KEV
не изолирует эффект RL. Обучение логитного scorer не называть rationale-RLCD.

## 10. Предлагаемый порядок проверки и критерии остановки

1. На development-состояниях, отделённых по исходным задачам, проверить
   построение C(h), аргументы, provenance и наличие приемлемого вызова.
   Отдельно посчитать, сколько решений тривиальны для правил, сколько требуют
   смыслового выбора, сколько пока непокрываемы. Не начинать с большого обучения.
2. Проверить A на ограниченном наборе обычных чтений; retrieval/discovery
   расширять отдельными условиями после проверки policy. Необратимые write-calls
   и свободные ответы на этом этапе остаются LLM.
3. Сравнить правила, KEV-4B и один совместимый Laya-вариант при одинаковой
   информации; подобрать routing вне test. Если модель не лучше правил по
   итоговому компромиссу качества/цены, не усложнять её ради обязательного использования.
4. Ввести B только там, где основной источник пропусков — множество возможных
   привязок. C/D вводить по обнаруженной причине, а не одновременно с A.
5. При достаточном покрытии и осмысленном модельном выборе зафиксировать узел
   и сравнить адаптацию; затем полные τ-knowledge диалоги с контролями и бюджетом.

Технический read-only пилот не гарантирует материал для трёх ВКР. Для
содержательного основного опыта нужны повторяющиеся нетривиальные выборы,
необходимые KB-условия и измеримый запас относительно правил/лексического
контроля. Три работы используют общую платформу; не обязательно заставлять
каждую ограничиться одним тривиальным lookup-микроузлом.

**No-go для выбранного узла:** недостаточный candidate recall; почти все решения
уже решены правилами; модель требует практически всегда fallback; или overhead
и последствия ошибок уничтожают экономию при согласованном качестве. Численные
границы и размер пилота ещё не выбраны; до test они должны быть зафиксированы.
Это повод пересмотреть контракт/область применения, а не скрыть невыгодные задачи.

Конкретные варианты A/B/C/D пока не утверждены. Следующее HITL-решение:
принимать ли A как базовый контракт и B как ограниченное расширение, оставив
процедуры и LLM-планирование последующими альтернативами.
