    Протокол данных, обучения и экспериментов System One

    Статус на 19.10.2026: подробное предложение для реализации исследования, подготовленное по запросу инициатора о дообучении на данных того же τ-bench. На момент подготовки этого протокола модели не запускались. По следующему поручению 19.10.2026 выполнен технический offline CE-пилот, с предварительной разметкой и ограниченной dev-таблицей; полная научная серия заблокирована валидностью данных и числом dev-групп. Численные бюджеты, доли разбиения и критерии перехода ниже — предлагаемые параметры протокола, которые фиксируются до окончательной серии. Список задач и их владельцы остаются в главной wiki.

    Этот документ конкретизирует личное направление адаптации оценщика контекста. Общая система, принятые границы ролей и точный контракт наблюдаемого входа сохраняются в постановке и контракте контекста v0. System One выбирает KB-доказательства; основная LLM продолжает вести диалог, искать информацию, выбирать инструменты и формировать их аргументы. Маршрутизация к LLM-селектору — отдельный фактор исследования.

    1. Проверяемый результат и границы утверждений

    Основной вопрос: улучшает ли адаптация одного компактного оценщика на банковских состояниях τ-knowledge качество отбора контекста и полную стоимость агента по сравнению с исходным checkpoint и LLM-селектором при одинаковой доступной информации? Второй вопрос: меняет ли ответ выбор CE или прямого Brier loss? Вопрос о рассуждениях проверяется отдельной серией, без смешения обучения учителя, архитектуры студента и режима работы основной LLM.

    Гипотеза Главное сравнение Что может её опровергнуть
    H1: банковская адаптация полезна Frozen и fine-tuned одного checkpoint, один вход и packer Offline улучшение не воспроизводится либо не переносится в полный агент
    H2: иной proper loss улучшает вероятности или компромисс риск–стоимость CE и Brier при одинаковых данных, параметрах и бюджете поиска После одинаковой post-hoc калибровки различия исчезают или хуже CE
    H3: рассуждающий teacher даёт более полезную supervision Direct и deliberate teacher на тех же train snapshots; одинаковый student inference Метки дороже, но не точнее; выгода не покрывает стоимость разметки
    H4: компактный селектор уменьшает полную цену LLM-context selector, frozen S1, fine-tuned S1; отдельно native/BM25 Стоимость actor, повторов, R-gate и fallback съедает экономию узла
    H5: качество сохраняется в допустимом диапазоне Парная разность native success и заранее выбранный допуск Нижняя граница CI ниже допуска либо интервал слишком широк
    H6, необязательно: rationale на inference взаимодействует с обучением Один генеративный backbone, одинаковый readout, прямое решение и rationale Эффект объясняется бюджетом генерации или сменой модели, а не objective

    H1, H2, H4 и H5 составляют законченную ВКР и при отрицательном результате. H3 и H6 — расширение после проверки источника меток, ресурса и мощности опыта. Идентификаторы H1–H5 совпадают с общим атласом. Новый алгоритм RL и обучение foundation model с нуля не нужны для завершения.

    Обобщение основной серии ограничено новыми отложенными банковскими задачами в известном синтетическом KB-мире, с выбранным actor, simulator, retrieval и бюджетом контекста. Оно не доказывает перенос в реальный банк, на произвольные LLM, на неизвестные документы или на другие домены. Общие документы KB в train и test допустимы для этого вопроса, но должны быть явно раскрыты.

    2. Проверенная исходная база

    Рабочий pinned benchmark — sierra-research/tau2-bench, commit 4ce7c0397c1eb65c9bbe59aeacfe1ca44a1cd699. Перед реализацией нужно сохранить его полный manifest, состояние локальных правок и лицензии. Это исследование текстового τ-knowledge / banking_knowledge, а не смешение всех исторических релизов под словом «tau-bench».

    По ресурсному аудиту на этой ревизии имеются 97 banking-задач и 698 KB-документов. Отдельного официального train/test для banking нет: get_tasks(task_split_name) читает все task_*.json, аргумент split пока не использует. Это повторно проверено по pinned loader. Исходные retail train 500 из старого τ-bench не являются banking train.

    Task содержит инструкции симулятору, начальное состояние, описание для оценщика, evaluation_criteria и список названий required_documents. evaluation_criteria.actions — одна референсная траектория; совпадение действий обязательно только при соответствующем reward_basis. Поэтому её нельзя механически превратить в единственно правильные метки каждого состояния. Семантика проверена по Task schema и описанию evaluator.

    Три слоя данных и право видимости

    Слой Примеры Кто получает Роль в обучении/оценке
    Мир и публичная политика Корпус KB, native policy, схемы разрешённых tools Среда; actor через штатный контракт, selector только через observed snapshot Один закреплённый KB для всех условий; его наличие не даёт selector права читать весь корпус
    Наблюдения диалога Реплики пользователя, ответы инструментов, уже возвращённые KB-записи Actor и детерминированная проекция для selector Единственные содержательные признаки основной модели
    Данные задания и эталона Сценарий симулятора, initial DB, purpose/notes, required_documents, reference actions, assertions Симулятор, среда, evaluator; отдельный offline-разметчик согласно split Помощь аудиту/разметке, никогда скрытая подсказка в model input

    Публичность test JSON в GitHub не делает его содержимое разрешённым признаком. required_documents относится к задаче целиком, а не к текущему ходу; это weak retrieval signal, не готовый binary gold. Список содержит названия: сопоставление с native document ID требует проверки уникальности и версии. Поля initial DB доступны actor только через разрешённые наблюдения; нельзя подставлять их в state builder напрямую. Будущая реплика пользователя также недоступна на текущем snapshot.

    Предлагаемая физическая граница: отдельно хранить observations/ и annotation_private/; training loader собирает input по явному allowlist. Unit-проверка сериализованного payload запрещает поля user_scenario, evaluation_criteria, required_documents, hidden DB и будущие event IDs. Названия каталогов — проект будущих артефактов, не уже существующая реализация.

    3. Разбиение до траекторий, учителя и калибровки

    Основной путь: собственный banking split

    Чтобы обучаться на той же предметной области, выделить собственные train / dev / test среди 97 задач до генерации rollout, пар кандидатов, teacher targets, перефразировок и hard negatives. Ориентир по числу задач — 60 / 20 / 20 процентов, то есть примерно 58 / 19 / 20 при отсутствии групповых ограничений. Это не готовый список ID: группы могут заметно изменить пропорции. Окончательные размеры — результат аудита, а не округление любой ценой.

    Все состояния, повторы, teacher-ответы, производные minimal pairs и аугментации одного источника наследуют его split. Не создавать «дополнительный test» перефразированием train-задач. После закрытия split нельзя переводить неудобные test-задачи в train ради улучшения результата.

    Порядок построения split

    1. Прочитать все задачи без rollout. Сохранить ID, file hash, тип reward_basis, короткую структурную аннотацию workflow, задействованные продукты/операции, сущности и связи с KB. Проверять корректность JSON и уникальность ID.
    2. Создать жёсткие группы происхождения: одна исходная задача и её варианты; одинаковый шаблон с подставленными числами/именами; почти одинаковые сценарии; задачи с одним клиентом/счётом/транзакцией, если состояние или решение одной раскрывает ответ другой. Эти группы никогда не разделять.
    3. Проверить near-duplicates нормализацией имён/чисел, символьными и словесными n-граммами, сравнением последовательностей операций и ручным просмотром подозрительных пар. Порог сходства выбирать на train-пилоте либо задавать заранее; не оптимизировать его по результатам моделей на test.
    4. Разделять конкретное семейство шаблонов и широкую рубрику вроде «карточная операция». Первое — жёсткая группа, второе — признак стратификации. Не объединять все задачи, использующие один общий policy-документ или tool, в один гигантский компонент. Иначе split может стать неосуществимым.
    5. Назначить группы в train/dev/test фиксированным алгоритмом и seed с разумным покрытием reward basis, длин, сложности, рубрик и количества KB-наблюдений, если последние доступны только как pre-rollout metadata. Не использовать успешность исследуемых моделей для балансировки.
    6. Сделать cross-split аудит текста, сущностей, шаблонов и производных записей. Сохранить решения по спорным совпадениям. Названия и содержание общих KB документов перечислить как разрешённое пересечение.
    7. Закрепить split_manifest и hash до учителя и обучения. Доступ к test-gold для разметки не превращать в доступ разработчика моделей: разметчик выдаёт test-labels только evaluator, а разработчику — заранее оговорённый отчёт.

    При сильной связности число независимых групп может оказаться значительно меньше 97. Это факт о мощности исследования; его нельзя скрывать количеством извлечённых candidate rows. Для отдельного заявления «перенос на новый workflow» нужен workflow-held-out анализ, в котором широкие семейства не пересекаются. Не называть основной task-held-out опыт таким переносом автоматически.

    Что делать с dev

    В dev разделить группы на dev_tune и dev_cal, ориентир — примерно поровну. dev_tune используется для learning rate, checkpoint, loss-настроек и prompt; dev_cal — для заранее выбранного способа temperature scaling и порога. На девятнадцати задачах это слабая база для уверенной калибровки, поэтому допустим заранее спроектированный grouped cross-fitting внутри train+dev. Он не даёт права выбирать процедуру по test. При недостатке независимых групп лучше ограничить вывод и оставить always_accept, чем заявлять гарантию риска.

    Для калибровки C и R нужны разные целевые события. Температура p(useful) не калибрует автоматически риск набора q(error_accept). Основная адаптационная серия сначала работает без обучаемого R, чтобы его ошибка не скрывала H1.

    Другие режимы, которые нельзя смешать с основным

    Режим Train Итоговая проверка Какой вопрос отвечает
    Основной in-domain Свой grouped banking train Отложенные banking задачи из того же KB Адаптация к известной области
    Сохранить все 97 banking как holdout Только другие native train домены или независимые banking-сценарии Все 97 banking Междоменный перенос либо перенос с новых сценариев; не обучение на самих 97
    Новый KB Отдельные документы/сущности/семейства Ранее не виденные документы Перенос знаний; отдельный дизайн и контроль решаемости

    Из одних 97 задач нельзя одновременно получить большой независимый banking train и сохранить все 97 как untouched test. Если test раньше обсуждался вручную, это раскрывается как риск human contamination; публичный benchmark также может входить в предобучение внешних моделей, что мы не способны исключить.

    4. Как собрать наблюдаемые состояния и кандидатов

    Минимальная последовательность: split → train/dev rollout → immutable snapshot → candidate table → annotation → quality audit → dataset release. Test rollout готовится отдельной замороженной процедурой и не используется для разработки.

    Этап Как реализовать Сохраняемый результат Проверка завершения
    Исходный rollout Native banking BM25, фиксированные actor/simulator, policy и seeds Полная native trajectory и журнал стоимости Native evaluator и история воспроизводимо читаются
    Снимок до решения После получения очередного batch сообщений, перед следующим actor-вызовом Cutoff, state, весь observed pool, бюджет, semantic hash Нет будущих событий, hidden fields, незавершённых tool pairs
    Нормализация KB Разобрать только реально полученный retrieval body; сохранить native ID/content hash/provenance Версионированные единицы пула Round-trip текста без дополнения скрытым corpus
    Допуск входа Полная сериализация state+candidate+instruction+options каждым tokenizer Token counts, overflow codes, representation version Runtime не выполняет незаметную truncation
    Отбор snapshots Стратификация по задачам, длине, этапам и ошибкам; ограничение похожих повторов Список отобранных snapshot_id и sampling weight Один длинный диалог не доминирует в dataset
    Разметка Рубрика evidence, границы применимости, проверка selected sets Labels с источником и неопределённостью Метку можно обосновать наблюдаемым текстом

    Первую коллекцию получить исходным агентом и одним заранее выбранным дешёвым контролем. Следующий train-only раунд может добавить состояния из adapted агента, чтобы уменьшить расхождение распределений, но это новая версия данных. Условия получения, доли источников и стоимость сохраняются. Не собирать только успешные эпизоды: нужны ошибки retrieval, недостающие условия и бесполезные кандидаты. Неуспех эпизода сам по себе не делает каждый его документ отрицательным.

    Offline test — один общий замороженный банк snapshots для всех методов. Full-agent test — отдельная on-policy оценка: действия меняют будущий диалог, поэтому пулы разных методов позднее закономерно различаются. Равенство информации проверяется на одном snapshot и контрактом, а не искусственным навязыванием одной траектории всем работающим агентам.

    Дубликат того же документа из нескольких поисков сохраняет все provenance, но не становится несколькими независимыми candidate rows. Если текст одного ID изменился, это отдельная версия. Старые невыбранные единицы остаются в пуле. Общая структурная нарезка применяется лишь если целая native запись не проходит admission, согласно контракту; parent header, offsets и соседние ограничения сохраняются. Проверяется качество полного входа, а не только длина документа.

    5. Что именно является обучающей меткой

    Семантическая рубрика пары и набора

    Для пары (s, d) целевое событие Y_useful=1 означает: в кандидате есть применимое доказательство для текущей наблюдаемой потребности, ограничения, исключения, следующего допустимого уточнения либо безопасного отказа. Просто совпадающее слово или упоминание темы недостаточно. Полезность относится к текущему state, а не к теме всего диалога. Не требуется, чтобы документ единолично гарантировал успешное завершение задачи.

    Поле аннотации Допустимые значения Назначение
    usefulness useful, not_useful, uncertain Основная target C; uncertain не кодируется молча как 0
    evidence_role rule, exception, precondition, procedure, tool_discovery, answer_fact, irrelevant, unknown Диагностика причины и сложных пропусков
    support_spans Offsets в наблюдаемом кандидате Проверяемость обоснования
    applicability Условия применимости и ссылки на наблюдаемые event IDs Не подменять предположение подтверждённым фактом
    coverage_groups ID атомарных требований и альтернативных доказательств Учитывать избыточность и взаимодополняемость
    label_source human, rule, teacher, counterfactual, weak_native Разделять происхождение и надёжность
    adjudication accepted, disputed, excluded Сохранение разногласий

    Для snapshot сначала сформулировать текущую потребность по наблюдениям и небольшой список атомарных требований: например, правило eligibility, его исключение, порядок проверки, необходимость согласия. Связь «требование → доказательства» может содержать альтернативные наборы, а не только один обязательный документ. Два дублирующих полезных документа не обязаны быть выбраны одновременно. Наоборот, правило и исключение могут быть полезны только в совместном наборе.

    Разделить три оценки:

    1. p(useful | s,d) — пригодность отдельного кандидата для потребности.
    2. sufficient(s,S,observed_pool) — содержит ли набор S достаточное покрытие той информации, которую можно установить из наблюдаемого пула, для заданного локального решения; значения yes / no / unknown.
    3. Native episode success — итоговый результат агента с tools и simulator.

    Если нужное доказательство вообще не найдено retrieval, selector не должен получать обвинение в его удалении. Отдельно размечать not_in_pool, lost_by_state_builder, lost_by_segmentation, lost_by_selector, actor_ignored_evidence, ambiguous_gold. Достаточность относительно пула не означает достаточность относительно всей KB и не гарантирует успех эпизода. Нативный reward хранится в episode table, а не размножается как target C.

    Контрфактические проверки

    Два вида проверки дополняют семантическую разметку и не заменяют друг друга:

    Локальная проверка доказательств. Для принятого набора удалить правило, исключение или целую альтернативную evidence group; затем проверить, остались ли все необходимые требования покрыты. Добавление случайного документа само по себе не делает набор лучше. Для альтернатив A/B проверять удаление обоих, поскольку leave-one-out каждого по отдельности может дать ноль. Так получается проверяемая метка потери evidence, без дорогого продолжения.

    Парное продолжение агента. На небольшой заранее выделенной train/dev подвыборке восстановить один и тот же cutoff, состояние среды, контекст симулятора и настройки. В одной ветви передать S, в другой S \ {d} либо S с добавленным кандидатом; сохранить остальное. После этого обе ветви идут самостоятельно. Для каждой использовать один и тот же набор продолжений и seeds там, где API действительно позволяет seed. Вычислять разность успеха, ошибок локального действия, затрат и задержки. Не оценивать такой эффект единственным lucky/unlucky продолжением.

    Если библиотека не умеет надёжно сериализовать состояние оркестратора и симулятора, сначала реализовать проверяемый replay до cutoff. Несовпадение state hashes запрещает причинное толкование. При воспроизведении через LLM seed не гарантирует идентичность даже при одинаковых настройках; сохранять ответы и фактические запросы. Reference actions применяются evaluator отдельно, их нельзя показывать actor при восстановлении.

    Контрфактический эффект зависит от actor и других документов. Его отсутствие не доказывает бесполезность: actor мог помнить правило, угадать или не справиться в обеих ветвях. Его наличие на одной ветви не доказывает универсальную необходимость. Такие наблюдения — отдельные targets/диагностика, а не автоматический истинный gold.

    Teacher, hard negatives и шум

    Teacher получает те же наблюдаемые state + candidate и рубрику. Для строгого сравнения источников supervision он не получает task-gold. При использовании gold-assisted annotation это отдельная метка provenance и отдельная серия: данные для объяснения полезности шире того, что видит student. Ответ teacher включает label, evidence spans, условия применимости и insufficient_information; уверенность teacher не считается вероятностью истины.

    Пилот: 200–300 проверяемых решений из train, затем независимый двойной просмотр стратифицированной подвыборки. Ориентир — не менее 20% пилота и все спорные случаи; перед большой разметкой оценить согласие по классам и типам доказательств. Сохранять raw agreement, confusion matrix, долю uncertain и причины разногласий. Высокая κ сама по себе не удостоверяет корректность рубрики.

    Полезные типы hard negatives:

    • Те же продукт/термины, но другая операция или клиентская категория.
    • Основное правило без применимого исключения; исключение с невыполненными предпосылками. Само правило может оставаться useful — не объявлять его отрицательным только потому, что одного правила недостаточно.
    • Устаревшая потребность после наблюдаемой смены темы, отзыва согласия или уточнения; сохранить ссылки на изменившиеся сообщения.
    • Документ для другого типа счёта/карты при лексически похожем запросе.
    • Высоко оценённый frozen scorer/BM25 кандидат, который разметчик признал неприменимым; добывать такие ошибки только внутри train.

    Синтетические перестановки условий и entity substitutions допускаются только в train и лишь после проверки непротиворечивости. Запись получает synthetic=true, parent_task_id, transformation, reviewer. Не редактировать тестовый KB и не выдавать искусственно испорченный документ за native наблюдение. Контрольный анализ исключает синтетические данные.

    Не уравнивать классы бесследным oversampling. Сохранять природную prevalence, sampling weights и причины отбора. Если train reweighting изменяет prior, проверять калибровку на естественном dev/cal. Loss CE и Brier получают одинаковый sampling protocol; иначе меняется сразу два фактора. Неразрешённые метки исключать из основного supervised loss и отчётливо считать; soft label давать только с описанным способом получения, а не назначать каждому спорному случаю 0.5.

    7. Обучение: от дешёвого контроля к адаптации

    Основной кандидат выбирается после admission/latency пилота по ресурсному обзору, а не по названию «System One». В первой причинной серии — один checkpoint и один набор обучаемых параметров. Сравнение default Laya с дообученным KEV не изолирует дообучение.

    1. Зафиксировать frozen checkpoint, tokenizer, шаблон useful / not_useful, порядок вариантов, полный preprocessing и максимально допустимый вход.
    2. На train-пилоте проверить targets и padding/masking. Для бинарного выхода использовать CE по двум logits либо эквивалентную BCE; выбрать одну реализацию и сохранить соглашение о положительном классе.
    3. Сначала обучить доступную голову при замороженном encoder. Затем, если learning curve и ошибка указывают на ограниченность признаков, сравнить адаптацию encoder/LoRA отдельной серией. Не менять loss и trainable modules одновременно в главном CE/Brier сравнении.
    4. Построить learning curve на 250 → 500 → 1000 → 2000 → 4000 размеченных train-парах при наличии достаточного разнообразия. Это ориентиры, не квота: четыре тысячи почти одинаковых пар не заменяют новые задачи. Выбор объёма и ранняя остановка — только по train/dev.
    5. Для выбранного объёма выполнить CE/Brier с 3 заранее заданными training seeds, одинаковыми датасетом, minibatch sampling, пределами tuning и критерием checkpoint.
    6. Сохранить raw probabilities. Затем одинаково провести temperature scaling на dev_cal и сравнить raw и calibrated результаты. Не подбирать разные процедуры калибровки для победы одного loss.

    Если default checkpoint уже поставляется с calibration scalars, сохранить отдельное условие default_published с ними: это измерение готового продукта. Для эффекта адаптации сопоставлять default_raw / adapted_raw, затем default + same_TS_protocol / adapted + same_TS_protocol на одном dev_cal. Не сравнивать свежекалиброванный adapted с необъяснимо иной shipped temperature и не приписывать всю разницу обновлению весов. Отключение или чтение встроенной калибровки должно быть подтверждено кодом конкретного runtime.

    Для binary target y и положительной вероятности p:

    [ L_{CE}(p,y)=-y\log p-(1-y)\log(1-p),\qquad L_{Brier}(p,y)=(p-y)^2. ]

    Brier для полного двухклассового вектора — сумма двух квадратов, равная 2*(p-y)^2; закрепить нормировку, чтобы изменение масштаба не выглядело новым алгоритмом. Вероятности для NLL ограничивать только численно обоснованным ε, одинаковым при отчёте; сохранять исходные значения и число предельных вероятностей. Class weights, label smoothing, focal loss и oversampling — дополнительные факторы, не молчаливые отличия CE/Brier.

    Proper loss — свойство ожидаемой цели, а не обещание идеальной калибровки обученной сети на малых или сдвинутых данных. В обоих методах нужен одинаковый бюджет подбора learning rate: одинаковая численная скорость обучения не всегда равна справедливой настройке целей с разным градиентом. Основной отчёт показывает как число обновлений, так и compute/time. Если сравнивается равный wall budget, это отдельная заявленная абляция.

Версия, тарифы и ограничения режимов записаны в реестре источников атласа. До запуска проверить доступ аккаунта и native adapter, закрепить provider, фактическую модель/revision, tools/reasoning controls, тариф и доступность seed. Выбор LLM actor и LLM selector — два отдельных поля. Если в разных arms заменить ещё и actor, эффект дообучения перестанет быть идентифицируемым. Actor reasoning mode также фиксирован в основной серии.

    Бюджет и fallback

    Стартовый профиль из общего контракта: KB-block 2048 токенов actor tokenizer, проверка чувствительности на 1024/4096 после основной серии; pointwise payload ориентировочно до 4096 токенов с проверкой всех внутренних sublimits. Числа не являются подтверждённой достаточностью. Показать долю snapshots, которые не проходят admission, отдельно для каждого условия.

    Основной опыт адаптации: always_accept для технически валидного отбора, одинаковая заранее заданная обработка технического отказа из общего контракта: передача того же snapshot LLM при допустимом входе, иначе явная техническая неудача. Semantic LLM-fallback и learned R здесь отключены. Техническую передачу считать отдельно от semantic defer и включать в стоимость; offline-метрики C показывать вместе с долей непригодных входов, а full-agent итог — на всех назначенных задачах. Дешёвый recency остаётся отдельным arm, а не скрытым спасением ошибочного C. Такая серия различает качество оценщика и результат системы с обязательной обработкой отказов.

    Следующая серия добавляет один замороженный R и одну процедуру калибровки порогов, не меняя C. При сравнении адаптаций допустима одинаковая процедура повторной калибровки на выделенном dev_cal; нельзя переносить старую температуру и объявлять плохую калибровку свойством нового loss. Отчёт показывает always_accept, always_LLM, cheap gate и выбранную policy, включая стоимость самого gate. Число fallback на 100 решений и на эпизод — разные показатели.

    9. CE, Brier, RLCD и рассуждения: отдельные оси

    Вероятнее всего, под «CD vs Brier» имелись в виду CE (cross-entropy) против Brier, либо RLCD. Это не одно и то же сравнение. CE/Brier задают целевую функцию. RLCD обозначает конкретный способ обучения распределений, и реализации различаются: шум в logits/gradient estimator у компактной модели либо генерация rationale у autoregressive модели. Разбор первоисточников — в обзоре обучения и обзоре RLCD.

    Минимальная основная матрица

    Loss студента Без teacher rationale С rationale у teacher
    CE CE × direct_teacher CE × deliberate_teacher
    Brier Brier × direct_teacher Brier × deliberate_teacher

    Это 2×2 по обучению, а student во всех четырёх клетках выдаёт распределение без генерации объяснения. Сначала выполнить CE/Brier на одинаковых проверенных human/rule targets; teacher-матрица включается после этого, чтобы не спутать эффект loss с качеством labels. Во второй серии teacher mode меняет только способ получения train targets. Рубрика, исходные snapshots и бюджет допустимых ручных исправлений одинаковы. Rationale сохраняется для аудита, но не становится новым полем student input на test.

    Если teacher API возвращает лишь итоговый ответ, не выдумывать скрытый chain of thought: фиксировать доступный reasoning mode, token budget и observable evidence justification. Режим «попросить подумать» не подтверждает одинаковый compute или фактический внутренний алгоритм. Измерять качество teacher labels по одному независимо проверенному подмножеству, затем downstream эффект.

    Если нужен именно inference с рассуждением и без него

    Laya encoder не имеет штатного autoregressive rationale. Добавить ему генерацию и сравнить с исходным Laya означает сменить архитектуру. Для H6 нужен один генеративный backbone с двумя режимами и одинаковым вероятностным readout:

    Фактор Уровни Что запрещено менять вместе с ним
    Цель обучения CE / прямой Brier; RLCD только отдельным третьим методом Данные, readout, backbone, trainable modules
    Supervision rationale Прямые метки / audited rationale+метки Источник задач, скрытая информация, число проверенных примеров
    Inference Прямое распределение / rationale → то же распределение Actor, пул, доступные сведения, evaluation task

    Полное произведение даёт минимум 8 условий до seeds и frozen-контроля. Не запускать его автоматически: сначала 4 клетки loss × inference при одном обучающем корпусе, если модель поддерживает оба режима. Отдельно проверить, не является ли отключение rationale на модели, обученной только с rationale, сдвигом распределения. Нужны direct-trained и rationale-trained контроли, если вывод касается именно влияния типа обучения.

    Rationale inference получает измеряемый лимит токенов и включает цену/время генерации. Основная LLM actor сохраняет тот же reasoning mode во всех клетках. Сравнение encoder S1 и генеративной модели — сравнение семейств, а не чистый эффект рассуждения. По источникам SBERT2S1 изучает typed encoder decisions, а OpenJev-RLCD — схему с rationale; их внешние результаты не являются измерением нашей банковской задачи.

    Для RLCD дополнительно закрепить reward, estimator, noise/group size, baseline/leave-one-out, KL/entropy terms, число sampled rationales и стоимость. Для Laya с непрерывным шумом в logits обязательный контроль — прямой или reparameterization gradient той же сглаженной proper-score цели при той же модели и данных. У OpenJev с дискретными sampled rationales полный gradient expectation содержит и gradient readout, и score-function term. Только direct readout без второго слагаемого не является полным градиентом той же задачи: это отдельная абляция отключения rationale policy learning. Сравнивать её с continuation из одного stage-1 checkpoint при одинаковом compute budget, с явно указанными KL и reward/cost terms. Иначе нельзя отделить выигрыш objective от estimator или дополнительного compute. CE+Brier mixture — отдельная явно названная цель, а не результат чистого Brier.

    10. Метрики узла, агента и всей исследовательской серии

    Уровень Основные метрики Условия корректного расчёта
    Разметка Доля accepted/uncertain, agreement, число независимых task groups, prevalence Отдельно human/rule/teacher/synthetic; не считать все строки gold
    C: вероятности Binary NLL, Brier, reliability plots; ECE как дополнительная Raw и calibrated; bins фиксированы заранее; неопределённость по task groups
    C: ранжирование PR-AUC при редких positive, recall/precision по кандидатам, nDCG при валидных graded labels Раскрыть класс и prevalence; не вычислять ranking gold из финального reward
    Набор Evidence coverage, доля пропущенных правил/исключений, set sufficiency, tokens saved Альтернативные evidence groups; отдельно случаи not_in_pool
    R/policy Risk–coverage, false accept, fallback rate, риск по типу пропуска R оценивает ошибку набора; не произведение p_i
    Агент Native success/reward, pass^k, termination/errors, DB/ACTION/NL компоненты Не менять native reward basis; инфраструктурные отказы отдельной строкой
    Задержка Selector, retrieval, actor, user simulator, evaluator; end-to-end p50/p95 Cold/warm и cache state; одинаковый параллелизм и режим оборудования
    Цена На решение, эпизод, успешный эпизод; разметка+обучение отдельно Все неудачи, retries, repair calls, discarded runs, fallback включены

    pass^k в τ-bench — устойчивость успеха в k повторах: для n trials и c успехов используется comb(c,k)/comb(n,k), а не вероятность хотя бы одного успеха pass@k. Native код отдельно исключает инфраструктурные ошибки из своей таблицы; наш дополнительный operational отчёт должен показать все запланированные попытки и понесённые затраты. Источник: agent_metrics.py.

    Среднюю success считать сначала по repeats каждой задачи, затем усреднять по задачам/заданным весам. Unequal repeats не дают «сложной» задаче больше веса случайно. Для latency показать оба взгляда: пользовательская задержка actor turn и длительность симуляции с simulator/evaluator. Среднее не заменяет p95. GPU time и сумма длительностей параллельных вызовов не равны wall clock.

    Пусть C_run включает все фактические расходы серии, а N_success — число успешных попыток. Тогда cost_per_success = C_run / N_success; при нуле успехов показатель не определён, а не равен нулю. Для deploy-анализа считать отдельно inference C, и C_total(N)=C_data+C_train+C_cal+N*C_inference. Окупаемость адаптации относительно frozen существует только при положительной экономии на inference и сопоставимом качестве; ориентир N_break_even=(C_data+C_train+C_cal)/ΔC_inference с неопределённостью всех частей. Локальные вычисления показывать в machine-hours и энергопотреблении, если оно измерено; отсутствие API-счёта не объявлять нулевой полной стоимостью.

    11. Статистический план и порядок выбора победителя

    Единица независимости — исходная задача/жёсткая группа, а не candidate row. Один диалог может дать десятки коррелированных snapshots и сотни пар. Разделять training seed, simulator seed, actor randomness и hardware repeats.

    1. До test назвать основную пару H1, основную метрику, направление улучшения, допустимую потерю агентного качества ε и minimum worthwhile saving. Число вроде ε=5 процентных пунктов — возможный проектный выбор, не уже доказанная достижимая точность.
    2. Все arms оцениваются на одних task IDs и назначенных simulation seeds. Порядок arms перемешивается блоками по задаче, чтобы изменение нагрузки API не совпало с условием. Одинаковый seed не гарантирует одинаковое поведение симулятора после разных действий; это парный дизайн по исходной задаче.
    3. Offline рассчитать разности метрик на общих snapshots. Bootstrap resamples task groups целиком со всеми их событиями, а не отдельные строки; сохранять спаренность предсказаний сравниваемых условий.
    4. Full-agent считать task-level средние и парные разности качества/стоимости. Для интервалов использовать cluster bootstrap по группам; повторы внутри группы сохранять вместе или применять заранее выбранный иерархический bootstrap. Не считать 3 repeats тремя независимыми новыми задачами.
    5. Три training seeds показывать отдельными точками и диапазоном; не выбирать лучший по test. Для full-agent можно заранее выбрать один seed и честно ограничить вывод, либо оценить все seeds с корректной двухуровневой неопределённостью. Повторять неизменный LLM baseline ради каждого training seed необязательно, но его общая зависимость сохраняется в анализе.
    6. CE/Brier и teacher-факторы анализировать через заранее заданные контрасты и interaction, показывая effect size и интервалы. При многих вторичных проверках указать multiplicity procedure либо маркировать их exploratory.
    7. Native failure, selector technical failure и infrastructure failure имеют разные категории. Retry policy и maximum attempts фиксируются заранее; не перезапускать лишь неудобные неудачные ответы до успеха.

    Около 20 независимых test-задач дают при success≈50% грубую обычную погрешность порядка ±22 п.п. до учёта кластеризации. Это иллюстрация масштаба 1.96*sqrt(0.5*0.5/20), не запланированный метод итогового CI. На таком test нельзя обещать доказать non-inferiority в 5 п.п. Повторы уменьшают шум конкретных задач, но не добавляют разнообразия workflow. Если мощности мало, публиковать интервалы и «неопределённо», а не превращать отсутствие значимости в равенство.

    Формальный итог качества: для ΔQ=Q_adapted-Q_baseline нижняя односторонняя граница CI должна быть выше -ε, чтобы заявлять выбранную non-inferiority. Экономию оценивать отдельно с интервалом ΔC. Если один критерий не подтверждён, вывод — ограниченное наблюдение или неопределённость, а не «качество сохранено». При малом числе групп нужен review устойчивости bootstrap и показ task-level результатов; красивый узкий интервал по тысячам зависимых строк недопустим.

    12. Ресурсные ворота и условия остановки

    Доступный проектный предел аренды GPU — до 30 000 ₽; лимит API ещё не установлен. Нынешний документ не разрешает платные запуски. Использовать имеющееся разрешение, если оно будет дано, без повторных микросогласований. Mac M4 Pro 24 GB — основной локальный ресурс; актуальные аппаратные варианты, включая дополнительный ПК, описаны в ресурсной оценке.

    Ворота Предлагаемый масштаб Условие продолжения Условие остановки/пересмотра
    G0: данные и видимость Полный статический аудит 97 задач, без моделей Есть split manifest, решаемая рубрика, чистая граница input/gold Утечка, смешанные ревизии, непонятный evaluator
    G1: локальный smoke 20–50 коротких пар, одна модель; затем 200–300 train labels Валидные вероятности, известны overflow/peak/time и качество меток NaN, silent truncation, неверный class mapping, swap/неустойчивая память
    G2: дешёвая learning curve Один loss/seed, 250–1000 train примеров Есть сигнал на dev сверх frozen/cheap controls Метки неоднозначны, ошибки state builder доминируют, качество не растёт
    G3: CE/Brier Один checkpoint × два loss × три seed Оба метода настроены в одинаковом tuning budget Расход/время выше замороженного cap, плохой data audit
    G4: полный агент 5–10 dev задач × 1–2 repeats, затем замороженный test Native паритет, рабочий журнал, оценена стоимость эпизода Ошибка семантики tools/evaluator или рост затрат без обещанного сигнала
    G5: reasoning/RLCD Только после G3/G4 и отдельной сметы Остался ресурс и есть конкретная неразрешённая гипотеза Расширение мешает завершить основную ВКР

    Порог acceptable agreement, доля overflow, peak memory и max duration выбираются после G1 до G2; их нельзя придумать задним числом для оправдания финальных метрик. Для конкретности предложенный локальный stop: при подтверждённой truncation или утечке немедленно остановить соответствующую серию; при устойчивом memory pressure/swap снизить batch/length в новой общей конфигурации, а не только в неудобном arm. Old runs остаются в журнале с причиной отбраковки.

    Платная смета считается по измеренному пилоту:

    • E_eval = N_test_tasks × N_arms × N_repeats; например, 20 × 6 × 3 = 360 эпизодов, сценарная арифметика, не выполненная серия.
    • E_collect = ceil(N_target_usable_snapshots / usable_snapshots_per_episode); usable yield измеряется, а не равен общему числу turns.
    • C_API = Σ_roles(input_tokens*price_in + output_tokens*price_out)/10^6 с отдельными cached tokens, retries и reasoning tokens, если они тарифицируются.
    • C_GPU = runtime_hours*hourly_rate + storage + transfer + idle_time.
    • Добавить teacher, counterfactual continuations, human labeling и резерв исправления ошибок. Тариф/валюта/дата и фактический bill сохраняются отдельно.

    Единое бюджетное предложение приведено в общем плане: 20% GPU-бюджета на профилирование/пилот, 45% на CE/Brier, 15% на повторения и 20% резерва. Это не поручение арендовать ресурс и не обязательство израсходовать весь лимит. API cap должен быть отдельным числом перед первым платным сбором. Автоматический stop выполняется до вызова, который превысит cap; резерв не тратится молча.
