    Ресурсы исследования τ-bench с Laya и KEV

    Статус: кабинетная проверка первичных model cards и кода на 11.10.2026; не локальный бенчмарк, не разрешение на расходы. Веса не скачивались, зависимости не устанавливались, обучение и платные вызовы не запускались. Документ фиксирует модели, память, объём данных, условные расчёты времени/цены и создаваемые компоненты. Факты источников отделены от наших плановых оценок. Уточнение по запросу 11.10.2026: проверен переход к выбору действия вместо binary gate. Аппаратные факты сохраняются, но объём action-разметки и память длинного контекста требуют нового пилота; 6000 — ориентир, не гарантия.

    Контекст: постановка, план RLCD, обзор τ-bench.

    Краткий вывод

    • MacBook M4 Pro / 24 GB достаточно для разработки и последовательного inference Laya / KEV-0.8B; KEV-4B через MLX выглядит реалистично. Последнее сильнее прежней гипотезы: автор измерил 4B на M5 / 32 GB с footprint 11.9 GB при 8k входе. Но это не замер M4 Pro и не гарантия пика при загрузке.
    • Laya head-only и короткое full fine-tuning теперь имеют открытый MPS-путь. Утверждение «есть только notebook для 2×T4» устарело: проверен отдельный MPS-скрипт. Это наличие кода, а не подтверждённые время/память обучения на нашем Mac.
    • KEV-0.8B LoRA — локальный малый пилот, не повторение авторского длинного рецепта. Последний занял 23.94 GB GPU памяти. Для 4B LoRA разумнее NVIDIA класса 48 GB после smoke-test; авторский пик 47.74 GB = примерно 44.46 GiB. Сверять доступную память карты в bytes и оставлять запас для allocator/контекста. Short-context рецепт может быть дешевле.
    • Full training KEV-4B на 24 GB исключается обычной арифметикой Adam. Обучение всей основы 0.8B теоретически помещается по состояниям параметров, но остаётся рискованным локальным экспериментом, не первым этапом.
    • Laya/KEV не заменяют генеративного агента и user simulator. Полностью локальный стенд возможен как отдельный конфигурационный эксперимент; достаточность памяти не подтверждает качество открытого симулятора.

    1. Какие версии проверены

    SHA фиксирует прочитанный снимок, а не доказывает запуск. HF API возвращает текущую ревизию карточки; для KEV она новее опубликованной ревизии весов, которую карточка прямо называет неизменной. При эксперименте закреплять runtime, adapter/head и backbone отдельно, не только имя модели.

    2. Архитектуры и три разных смысла обучения

    Семейство Что фактически вычисляется Что нельзя приписывать
    Laya Bidirectional encoder ModernBERT-large / mmBERT-base, два transformer-слоя одной головы принятия решений, scorer маркеров вариантов; один batched forward, без генерации rationale. Текущий train loss: шум Gaussian в logits + proper reward + policy-gradient term и soft CE; отдельно доступен soft-CE контроль. Это не OpenJev с генерацией цепочек рассуждений; четыре noise samples не означают четыре авторегрессионных rollout.
    KEV-0.8B / 4B Замороженная Qwen3.5 + LoRA rank 16, α=32 + pointer head; prefill и распределение по вариантам. Релизные модели обучены supervised cross-entropy, затем temperature scaling. Наличие типизированных вероятностей не делает этот SFT-рецепт RLCD.
    OpenJev-RLCD Генерирует rationale, читает распределение после Answer; proper score используется для readout и затем rationale policy. Его стоимость generation/group samples нельзя оценить одним forward Laya или KEV.

    Источники: Laya train, Laya архитектура, KEV карточки, KEV train, OpenJev README @ 22db40ad. Короткие цитаты: Laya — «a policy-gradient term over noisy logits plus soft cross-entropy»; OpenJev — «The model samples a rationale»; KEV — «The loss is cross-entropy over each question's options».

    Контекст — четыре разных ограничения

    Модель По умолчанию / лимит runtime Что действительно подтверждено
    Laya English 421M 512 токенов на вопрос, head budget 192, состоянию примерно 320 Увеличение окна основы само по себе не подтверждает качество English checkpoint на длинных входах.
    Laya multilingual 322M 1024, head budget 256; явно max_len=8192, состоянию примерно 7936 Небольшой авторский probe: 16–18 правильных из 20 примерно до 4k, далее 8–17/20. Не широкий long-context benchmark. Для английского длинного текста явно выбирать multilingual.
    KEV-0.8B / 4B Основа 262144; runtime state ≤65536, row state+question ≤73728 Обучение state ≤7552; обе текущие cards называют validated context 8192. У 4B уже 16k не прошло заранее заданный допуск качества.

    Источники: Laya card, multilingual, KEV model constants, 0.8B, 4B, Qwen configs. Описание инструментов, инструкции и варианты тоже расходуют окно. Одновременные вопросы увеличивают batch/число ветвей; «один вызов API» не значит константную память. Для τ-bench нужно явно формировать состояние узла, а не молча обрезать историю до первых 320 токенов.

    3. MLX, MPS, dtype и зависимости

    Laya. Проверенный путь Apple — PyTorch/MPS, не MLX. Файлы весов в основном FP16, но обычная модель строится в FP32; размер файла не равен resident RAM. В README есть устаревшее обобщение «CPU and MPS run fp32», однако текущий agent.py и подробный precision-раздел уточняют: на MPS FP16 autocast включается от 5 question rows; меньшие вызовы FP32. Поэтому agent.dtype показывает цель autocast, а dtype_for(rows) — режим конкретного вызова. При неподдержанном autocast возможен возврат в FP32; это нужно логировать. TileLang fast path — CUDA kernels/graphs, не ускорение Metal. Обычный encoder использует SDPA; для experimental parallel option layout есть собственные ограничения eager/transformers, он не нужен первому пилоту.

    KEV. MLX backend выбран автоматически для Qwen3.5 serving на Apple Silicon; использует BF16 основу, слитую LoRA, FP32 pointer head, chunked prefill по 1024 токена и ограничение MLX buffer cache 1 GiB. Фраза кода «MPS has no Gated DeltaNet kernels» означает медленный reference PyTorch-путь, а не отсутствие GPU вообще. MLX inference не означает MLX training: train.py обучает через PyTorch. Его --dtype bf16 явно требует --device cuda; --weights_dtype задаётся отдельно и по умолчанию fp32. На MPS короткий LoRA-пилот поэтому начинается с FP32, не с арифметики BF16 serving.

    KEV model.py выбирает eager attention на MPS/CPU и SDPA на CUDA для произвольной additive mask. Старые attention-only основы используют block-causal 4D mask [B,1,L,L]; гибридная Qwen3.5 не может применить её к рекуррентным DeltaNet-слоям, поэтому вопросы идут отдельными causal rows. В serving состояние кешируется; training без shared-prefix может повторно вычислять state на каждый вопрос. Сам dense FP32 mask 8192² — 0.268 GB на строку ещё до attention scores; наличие linear attention не устраняет все квадратичные члены и активации.

    CUDA serving использует flash-linear-attention/fused DeltaNet и CUDA graphs; это не зависимости, которые нужно пытаться установить ради MPS. Проверенный README KEV рекомендует flash-linear-attention именно на CUDA, а pyproject подключает mlx-lm 0.31.3–<0.32 для Darwin arm64. На Mac сначала проверять поддерживаемый backend, dtype, operators и реальные результаты; CPU fallback не выдавать за быстрый Metal inference.

    4. Что авторы действительно измерили

    Все строки ниже — внешние авторские результаты, не измерения нашего M4 Pro. Латентность модели не включает всю агентную оркестрацию; cached state и new state принципиально различны. Длинный кеш применим только при повторном использовании совместимого prefix, не ко всем ходам диалога автоматически.

    Laya multilingual, Apple GPU (точная модель в карточке не названа) Около 1.7 s на вход 4k Нельзя представлять как замер именно M4.

    KEV-4B LoRA, base H100 / skills H200 Base ≈56 min, peak 24.6 GB; skills 5031 s ≈1.4 h, peak 47,737,451,520 bytes, batch 2, 1915 steps Обычная 24 GB GPU не гарантирует даже точное повторение base-рецепта.

    Источники: Laya card, KEV-0.8B card, KEV-4B card, сырые training metrics 0.8B, 4B. Пик device и process RSS на NVIDIA — разные пулы; на Apple CPU/GPU делят unified memory.

    У KEV BF16 и FP32 не побитово эквивалентны: на короткой MLX проверке автора 0.8B изменился 1 ответ из 100, max |Δp|=0.020; у 4B 0 из 60, max |Δp|=0.018. Это аргумент фиксировать dtype и отдельно проверять калибровку, не гарантия паритета на τ-bench. KEV-0.8B card прямо пишет «Do not use it for tool-call routing»: When2Call test 0.133 при случайном выборе 0.25. Низкая цена не компенсирует непригодность исходного checkpoint к конкретному узлу.

    5. Нижняя граница памяти: только состояния параметров

    Единицы: GB = 10⁹ bytes; GiB = 2³⁰ bytes. Это не peak и не потребность в установленной RAM. Пусть N — обучаемые параметры при full FT, A — число обучаемых параметров при frozen backbone. Без активаций и временных копий:

    • inference: FP16/BF16 веса 2N; FP32 — 4N;
    • full Adam, FP32 weights+grads+два FP32 moment: (4+4+8)N = 16N;
    • условный mixed режим без отдельной master copy: (2+2+8)N = 12N;
    • BF16/FP16 weights+grads + FP32 masters+moments: (2+2+4+8)N = 16N;
    • frozen backbone N и FP32 trainable A: bN + 16A, b=2 или 4.

    12N — оптимистическая арифметическая граница выбранного режима, не обещание, что конкретный optimizer хранит именно так. В KEV full_ft код предусматривает FP32 masters; перенос optimizer на CPU не освобождает физическую unified RAM Mac.

    Модель / N для расчёта Только веса 16 / 32 bit, GB Full: 12N, GB Full: 16N, GB
    Laya English, 421,293,827 параметров (+3 FP32 calibration scalars) 0.843 / 1.685 5.056 6.741
    Laya multilingual, 321,908,995 (+3 scalars) 0.644 / 1.288 3.863 5.151
    KEV-0.8B, text backbone ≈0.752B ≈1.505 / 3.010 ≈9.03 ≈12.04
    KEV-4B, text backbone ≈4.206B ≈8.412 / 16.823 ≈50.47 ≈67.29

    Laya counts взяты из HF metadata English / multilingual. KEV N — расчётная оценка text architecture, не выполненный numel(): embeddings + MLP + full-attention и DeltaNet projections по конфигурациям (4B); согласуется с авторскими ≈1.5 / 8.4 GB BF16 weights. Округление и небольшой pointer head не меняют вывода. HF total whole-checkpoint 0.873B / 4.660B включает другие компоненты базовой multimodal модели; нельзя молча считать всё это resident KEV backbone или использовать имя «4B» как точный N. При реальном smoke-test дополнительно фиксировать sum(numel), реально загруженные модули и peak загрузки, не только steady-state. Во время загрузки/merge возможны копии.

    Head-only, LoRA и full — не взаимозаменяемые режимы

    Режим Нижняя оценка состояния параметров Реальная поддержка / ограничения
    Laya frozen encoder, FP32 head English ≈2.00 GB; multilingual ≈1.47 GB TrainConfig.freeze_encoder и detach_encoder реализованы. «Голова» включает 2 transformer-слоя, примерно 26.51M / 14.97M параметров, не только последний linear. Это расчёт по common.py.
    Laya LoRA Зависит от target modules и rank, отдельная оценка после выбора В проверенном штатном TrainConfig готового LoRA-рецепта не найдено. Не подменять им доступный head-only/full.
    KEV head-only, FP32 backbone ≈3.02 / 16.84 GB для 0.8B / 4B Pointer head H=2(d×256+256): 0.525M / 1.311M. Нужен явно frozen backbone/adapter, no_grad или detached features; штатный --lora 0 не является head-only режимом (CLI требует positive rank).
    KEV LoRA+head, FP32 backbone ≈3.20 / 17.38 GB A≈11.3M+0.525M / 33.8M+1.311M; BF16 frozen backbone дал бы ≈1.69 / 8.97 GB, но это не MPS default.
    KEV full FT См. 16N выше; плюс небольшая head Текущий train.py уже имеет --full_ft, MasterAdamW и FSDP2. Наличие функции не доказывает пригодность Mac; 4B не помещается даже без активаций.

    Head-only дешевле LoRA не только optimizer: frozen encoder можно считать без backward graph. При LoRA градиент проходит через основу к адаптерам, поэтому нельзя удалить все активации аргументом «основа заморожена». У KEV штатный MLX scoring не даёт end-to-end MLX autograd через Torch pointer head; перенос обучения туда — отдельная инженерная работа.

    6. Практические диапазоны для планирования, не измерения

    Ниже — оценочные envelopes процесса, не дополнительные факты авторов. Условие: один процесс/модель, batch 1, один или немного вопросов, короткий вход 512–1024, без параллельных генеративных LLM. Для обучения — checkpointing, небольшой microbatch; gradient accumulation повышает effective batch, но не превращает большой физический batch в бесплатный. Длинные входы меняют диапазон.

Не обещать время обучения M4 масштабированием только по FLOPS H100.

    Для будущего smoke-test достаточно измерить cold load, warmed p50/p95, process footprint/MLX peak/MPS allocated+driver memory, memory pressure/swap, input tokens × questions, dtype, backend и явные fallback. Сначала 512–1024, затем 2k/4k/8k там, где это содержательно допустимо. Здесь такие запуски не выполнялись.

    Дополнительный ПК с GTX 1660

Аппаратные источники проверены 19.10.2026.

Полноценную серию адаптации компактных оценщиков можно планировать на этой паре; для генеративного агента и симулятора сохраняется отдельная проверка качества и ресурсов. Перед выбором основной машины измерить peak memory и время шага одного и того же короткого опыта.

    7. Граница all-local agent + user simulator

    Laya/KEV возвращают распределения, но не генерируют реплики пользователя, текстовые ответы или произвольные аргументы tools. Для полностью локальной серии нужны отдельно генеративный agent, user simulator, оркестратор, retrieval и оценка. Один и тот же сервер LLM может обслуживать роли последовательно с разными history, но надо проверить контекст, доступность нужного API и отсутствие смешения диалогов; общие веса не делают simulator эквивалентным эталонному.

    Арифметика как пример, не рекомендация непроверенного checkpoint: две отдельные 8B LLM в 4 bit — минимум 8 GB только packed weights, плюс quantization scales, KV caches, buffers. Вместе с KEV-4B BF16 это уже ≈16.4 GB до ОС и runtime; такой одновременный набор на 24 GB рискован. Одна shared 8B 4-bit модель (≈4 GB raw weights), последовательные роли и Laya/KEV-0.8B оставляют больше запаса. При offload/reload учитывать wall time, а не исключать переключения из стоимости. Качество reasoning/tools и правдоподобие user simulator всё равно требуют отдельной валидации.

    Поэтому честный первый план — локальные decision models + независимо проверенный генеративный backend, затем отдельная all-local абляция. «Open-source через удалённый API», «локальный агент» и «весь стенд локально» — три разных условия; затраты симулятора и оценщика нельзя опускать.

    Это плановый ориентир, не готовый upstream dataset и не доказанный минимум:

    Часть Целевое число размеченных решений Назначение

    Начинать с learning curve 250 → 500 → 1000 → 2000 → 4000 на train/dev: не размечать все 6000 заранее, если небольшой пилот выявит непригодный узел. Кривую сначала строить для одного дешёвого метода, не умножать весь grid на все объёмы. 4000 — небольшой domain adaptation, не обучение новой foundation model. При среднем компактном входе 512–1024 токена все 6000 записей дают примерно 3–6 млн входных токенов; полные траектории хранятся отдельно.

    Одна запись решения: наблюдаемое состояние до действия, вопрос, варианты/ кандидат действия, рубрика, метка и источник её обоснования. Пограничные случаи и недостаточность наблюдаемой информации не принуждать к уверенной binary gold. Native финальная награда, schema validity и единственная reference trajectory не являются разметкой семантической допустимости каждого шага. Оценивание upstream.

    Откуда получить данные, не испортив test

    Более дешёвый первый путь — явный transfer: использовать 178 native train задач текущего τ³ для train/dev/cal с группировкой до rollouts; все 97 banking задач оставить нашим финальным holdout. Это проверка переноса между доменами, не in-domain calibration банковского узла. Гарантию риска на banking из калибровки retail/airline/telecom не выводить.

    Если нужна банковская адаптация: дополнительно создать train-only сценарии по публичным policy/KB с валидными initial states, user flows и reference checks. Генератор не получает инструкции/gold банковских test-задач. Нужны аудит решаемости и проверка near-duplicates. Общая база знаний допустима при заявленном обобщении на новые задачи, но это не unseen-knowledge experiment. Исходные 500 retail train можно использовать только как явно объявленный перенос с проверкой совместимости версий и пересечений, не выдавая за native train текущего τ³.

    При ограничении только имеющимися 97 banking-задачами придётся выделять собственные grouped train/dev/cal/test ID. Тогда финальный test существенно меньше 97 и статистическая мощность ниже. Получить одновременно большой независимый банковский train и полный untouched test только из этих 97 нельзя.

    Все повторы, состояния, отрицательные кандидаты и перефразировки исходной задачи идут в один split. При заявке на новые workflow делить также по семейству workflow; для обычного task-generalization явно раскрывать общие семейства. Разбиение строк случайным shuffle недопустимо. На offline test использовать одинаковый фиксированный пул состояний для всех моделей; full-agent on-policy траектории — другая, отдельная оценка.

    1000 test-решений не гарантированы. Если 97 задач дают меньше пригодных узлов, публиковать фактическое число, не добирать искусственными test-копиями. Интервалы кластеризовать по исходной задаче/семейству, а не по строке. Для ориентира 97 независимых задач около 50% успеха дают обычную 95%-ю погрешность порядка ±10 п.п.; повторы не превращают их в тысячи независимых задач.

    Стоимость создания данных в человеческом времени

    Если проверка одного решения занимает 1–2 минуты, полный ручной просмотр 6000 решений потребует 100–200 человеко-часов. Это сценарная арифметика, не измеренная производительность; сложные policy cases и второй annotator увеличат время. Автоматические проверки preconditions и программно размеченные minimal pairs могут уменьшить работу, но экономию подтвердить пилотом. Teacher LLM не считается бесплатным и безошибочным разметчиком. В этой ВКР корректная разметка может быть труднее и дороже вычислений.

    9. Сколько вычислений потребуется всей серии

    Обучение маленькой модели

    Минимальная причинная серия: один Laya checkpoint, один и тот же набор обучаемых параметров, CE / прямой Brier / конкретный Gaussian-logit RLCD, 3 training seeds, одинаковый calibration protocol. KEV-0.8B и KEV-4B — внешние reference models, их не обязательно тоже дообучать. Сравнение готовых Laya и KEV само по себе не изолирует RL от архитектуры и обучающих данных.

    Для 4000 train decisions, 3 epochs, 3 методов × 3 seeds:

    • 9 основных запусков, 12000 предъявлений примеров на запуск;
    • 108000 предъявлений в серии, без tuning/validation;
    • при effective batch16 — около 750 optimizer steps на запуск, если одна запись означает одну training decision и last batch обработан обычным образом.

    Скорость пока неизвестна. Чувствительность расчёта, не прогноз M4 Pro:

    Измеренная end-to-end training скорость Один run Все 9 runs
    1 example/s 3 ч 20 мин 30 ч
    5 examples/s 40 мин 6 ч
    20 examples/s 10 мин 1.5 ч

    Validation, checkpoint IO и прогрев добавляются. Если скорость ниже 1 example/s, время соответственно больше. Tokens, batch, trainable layers и loss должны входить в измеряемую скорость. Noise group=4 в Laya не означает автоматически четыре полных encoder forward. Learning curves и debugging — дополнительные серии, для которых нужен отдельный лимит, не «бесплатный tuning».

    Полные агентные диалоги

    Число эпизодов оценки: N_tasks × N_configurations × N_trials.

    • Малый smoke-test: 10–20 не тестовых задач, 1–2 повтора, 1–2 конфигурации.
    • Основной пример: 97 × 4 × 3 = 1164 полных диалога.
    • Четыре повтора вместо трёх: 1552 диалога.
    • Checkpoints разных training seeds — дополнительные конфигурации. Если все четыре условия проверять в трёх training seeds, верхний простой расчёт станет 3492 диалога; не дублировать неизменный baseline ради формального числа.

    Сначала сравнить все методы offline, затем перенести 3–4 заранее выбранные конфигурации в full-agent. Не выбирать seed по test; допустим заранее заданный seed для основной агентной серии с честной оговоркой и offline-разбросом всех seeds.

    Измеренное среднее wall time полного эпизода 1164 последовательных эпизода
    1 минута 19.4 часа
    3 минуты 58.2 часа
    10 минут 194 часа

    Это арифметические сценарии, не опубликованные скорости M4 Pro. Уже поэтому «модель помещается» не равно «вся серия закончится за вечер». Полное wall time включает агента, симулятор, tools, scorer, retries и evaluator; в научных метриках отдельно показывать latency самого агента.

    Обучающие данные требуют дополнительных диалогов. При q пригодных уникальных размеченных узлах на эпизод: E_collect ≈ ceil(5000/q) для train+dev+cal. Например q=3/5/10 означает примерно 1667/1000/500 эпизодов. Это условие расчёта; реальное q измерить на пилоте, не принять число всех turns за число usable labels. Программные minimal pairs можно создавать без нового полного диалога, но они не добавляют независимых сценариев. Во всех бюджетах учитывать discarded runs.

    Цена API и аренды

    Open-source weights не означают бесплатный inference. Для внешнего хостинга:

    $$ C_{API}=\sum_{r\in{agent,user,judge,teacher}} \left(\frac{T_{in,r}P_{in,r}+T_{out,r}P_{out,r}}{10^6}\right). $$

    Пример только для понимания масштаба: 20 суммарных agent/user вызовов за эпизод, по 4000 входных и 150 выходных токенов, на 1164 эпизода дают 93.12 млн input и 3.492 млн output tokens. Это не наблюдаемый workload. Цена получается только после выбора модели/провайдера/тарифа, cache policy и измерения токенов. Сбор train, teacher labels, повторы и judge сюда автоматически не включены.

    GPU-лимит проекта 30000 ₽ разумно оставить на одну выбранную модель и короткие серии, не тратить на воспроизведение обучения всех KEV. При условном тарифе r ₽/ч доступно 30000/r часов до хранения и прочих сборов. Например r=500 даёт 60 часов — это арифметический пример, не проверенный текущий рыночный тариф. API-лимит отдельно ещё не установлен; его нельзя считать включённым в GPU-лимит. Для Laya/малой LoRA первый класс аренды — 16–24 GB с пилотом памяти, для KEV-4B короткой LoRA — класс 48 GB с пилотом; авторские 47.7 GB ≈44.5 GiB, а фактически доступный запас зависит от карты, allocator и конфигурации.

    Если всё-таки воспроизводить именно OpenJev

    Это отдельная reasoning-ветка на Qwen3-1.7B, не обучение Laya/KEV тем же кодом. Автор сообщает 48 GB GPU и 1–1.5 часа на 400-step run плюс evaluation. Закреплённый OpenJev README. Для stage1, readout-continuation и stage2 в трёх seeds получится 9 таких стадий, то есть 9–13.5 часов только если сохраняются авторские hardware/workload. Наши длинные agent states, дополнительные контроли и rollout/evaluation могут радикально изменить цифру. На Mac 24 GB точное full-weight воспроизведение исходного рецепта не планировать. QLoRA/MLX-порт — другой инженерный эксперимент, не бесплатный способ объявить репликацию выполнимой. Если центральный вопрос именно о rationale-RL стадии, эту GPU-ветку нельзя молча заменить Gaussian-logit RLCD и сохранить тот же claim.

    Сценарий Что локально Что остаётся вне Mac Вывод

    Точное reasoning-RLCD / тяжёлое дообучение Разработка, подготовка, анализ NVIDIA GPU для OpenJev и тяжёлых KEV training recipes Одного M4 Pro24GB недостаточно для исходной полной программы

    В all-local нужен генеративный backend с корректным tool calling, не Laya в роли чат-модели. Небольшой 4–8B quantized checkpoint — класс для пилота, не выбранная и доказанно достаточная модель. Один сервер может последовательно обслуживать agent/user с разными независимыми history. Это экономит веса, но не отменяет KV/prefill, увеличивает wall time и может давать коррелированные ошибки ролей. Не держать Laya, KEV0.8, KEV4 и несколько LLM в памяти одновременно. Во время full fine-tuning выключить генеративные серверы.

    Для local baseline явно выбрать BM25. Upstream default alltools включает embeddings API/shell, а некоторые reranker-конфигурации — внешние API. Retrieval configs. Пользователь в τ-bench — LLM-симулятор с инструментами, а не статическая заготовка текста. Код симулятора. Banking: 87 задач reward DB, 9 ACTION, 1 DB+NL_ASSERTION; нельзя убрать последнюю из теста ради объявления «вообще без judge». Открытый judge backend выбирать штатной конфигурацией и фиксировать одинаковым для сравниваемых агентов; не менять критерии или код evaluator. Диагностические nonempty NL assertions зависят также от выбранного evaluation type. Оценивание, evaluator.

    Upstream модельные defaults не обязаны быть открытыми; их нельзя молча оставить и назвать серию open-source. Фиксировать открытые agent, user, judge и их лицензии/revisions. Defaults. Замена simulator/evaluator LLM — изменение протокола: результаты не являются точной репликацией leaderboard.

    Диск и ежедневная эксплуатация

    Планировать 50 GB свободного SSD для пилота, около 100 GB для основной работы: выбранные веса, HF cache, virtual environments, checkpoint exports и traces. Это резерв, не измеренный размер. Сам компактный decision-dataset — обычно порядок десятков/сотен MB в зависимости от сохранения контекста; сырой JSONL с повторяющимися длинными prompts легко становится больше. Периодические full optimizer checkpoints способны потребовать дополнительные десятки GB. Оставлять только нужные контрольные точки по заранее заданному retention policy, хранить hash/manifest; не коммитить веса и сырые большие выгрузки.

    11. Какие структурные элементы будут созданы

    Не новая foundation model и не собственный аналог всего τ-bench. Нужны следующие научные и программные артефакты; сейчас это проектируемые элементы, кода ещё нет.

    Элемент Что создаём сами Что переиспользуем
    1. Постановка и protocol manifest Target события, гипотезы, splits, риск/качество, лимиты, seeds, hashes Проектную методику, определения native metrics
    2. Dataset решений Извлечение состояний, provenance, каталоги действий, рубрика приемлемых next steps/неоднозначностей, аннотации и grouped splits Native tasks, KB/policies; train-only генераторы только при необходимости
    3. State builder Явный компактный вход узла; учёт потерянных фактов и context overflow Траекторию upstream и уже доступные policy/retrieval результаты
    4. Адаптер агента Один заменяемый selector следующей операции через HalfDuplexAgent Runner, среду, инструменты, симулятор и native evaluator τ-bench
    5. Унифицированные scorers Адаптеры Laya/KEV/дешёвого контроля; raw probabilities, dtype/backend и ошибки Готовые checkpoints и runtime, без переписывания нейросетей
    6. Calibration и fallback Калибровка определённого события, fixed fallback, цена неверного выбора и ошибки делегата Существующие математические методы, не новый фреймворк
    7. Training recipes Один backbone/head, сопоставимые CE/Brier/выбранный RLCD, seeds и checkpoints Laya MPS trainer / KEV LoRA при отдельной гипотезе
    8. Журнал всех вызовов JSONL traces: token/time/cost/memory, retries/fallback, task/run/model IDs Native messages, дополненные расходами внутренних узлов
    9. Два уровня evaluator Offline Brier/NLL/AURC/рабочие пороги и paired full-agent comparison Native DB/ACTION/NL success, без изменения gold
    10. Воспроизводимый отчёт CLI/config для серий, таблицы/графики, интервалы, ошибки, model/dataset cards Простые Python-команды и wiki проекта

    Минимальный runtime flow:

    Native τ-runner + user simulator
          ↓
Наблюдаемая история + доступные правила + каталог известных операций
          ↓
Фиксированный state builder
          ↓
Сменный scorer: правило / Laya / KEV
          ↓
Выбор ID операции + calibration/fallback выбора
          ↓
Фиксированный generator args/реплики, исходный scaffold и tools τ-bench
          ↓
Native evaluator + наш журнал узлов/стоимости/времени

    Fallback и generator зафиксировать одинаково для сравниваемых selectors. Native LLM выбирает имя и аргументы одним вызовом; выбор имени маленькой моделью не устраняет автоматически генерацию аргументов. Нужны native joint baseline и факторизованная LLM со сменным selector, плюс дешёвый контроль. Экономию оценивать относительно обоих; эффект новой факторизации не приписывать способу обучения. Полный протокол — в проверке action selection.

    State builder важен из-за окна Laya: нельзя скрытно обрезать policy до 320 токенов, а потом сравнить с KEV, которому дали весь диалог. Основная причинная серия использует одинаковую наблюдаемую информацию и token budget; длинный режим — отдельная абляция. Потерянная информация и стоимость её получения фиксируются. Для KEV адаптер использует распределения, а не считает нормированное choice.confidence готовой оценкой вероятности корректности.

    Не нужны для первой ВКР: новый web-интерфейс, Kubernetes, distributed vector DB, свой пользовательский симулятор, собственный движок benchmark, обучение всех размеров KEV, multi-agent swarm. Простейший воспроизводимый пакет/CLI достаточен. Общие компоненты и личный вклад учитывать по правилам команды.

    12. Рекомендуемая конфигурация и точки принятия решений

    1. Один selector следующей операции, один основной текстовый τ-knowledge домен; retail/native train — отладка и явно объявленный источник transfer.
    2. Одна Laya для причинного training-сравнения; начать с frozen encoder, затем короткий full FT, если это нужно гипотезе. Для русского/длинного входа выбрать соответствующий checkpoint явно, не надеяться на auto-routing.
    3. KEV4B и Laya multilingual для routing-пилота; KEV0.8 — дешёвый/отрицательный reference, его card прямо не рекомендует tool-call routing. Для Laya English и typed нужен явно compact input; policy-only уже превышает их default окно.
    4. Один простой контроль: правила или frozen embeddings + logistic regression.
    5. 200–300 размеченных pilot decisions, затем target около 6000 только если learning curve, разметка и вопрос оправдывают такой объём.
    6. На Mac — development, последовательное scoring, calibration и Laya training smoke-test. Удалённый open-weight agent/user — практичный основной вариант, all-local — отдельная абляция после проверки simulator fidelity.
    7. В full-agent переносить 3–4 условия; на 97 задачах с 3 trials это 873–1164 эпизода, плюс сбор данных. Дорогую learning curve всех моделей не обещать.
    8. До платной серии провести 50–100 training steps и 10–20 non-test задач: измерить peak/cold load, usable decisions per episode, token/time/cost каждого участника. Если прогноз превышает лимит или память уходит в swap — сокращать scope либо выбирать подходящую GPU, не делать test тюнинговой площадкой.

    Итог: новый компьютер для разумно ограниченной ВКР не требуется. Полностью на одном M4 Pro24GB можно пробовать компактный вариант с Laya и небольшими локальными генеративными моделями, но не обещать заранее качество симулятора, срок полной серии и репликацию OpenJev. Наиболее устойчивый план — Mac как основная машина, отдельный ограниченный GPU/API-резерв и переход к нему только по замерам. Главный риск — корректный dataset и протокол, а не место для KB.

    13. Уточнение: что именно означает validated 8192 у KEV-4B

    Проверено 11.10.2026 по pinned card 6cfce5c2 и коду 2ecafc49; не наш модельный прогон. Изначально это проверка достаточности входа для предлагаемого сравнения RLCD с CE/Brier. После уточнения личной темы она остаётся ресурсной проверкой общего узла, а не решением выбрать RLCD или новую context/action architecture.

    • 8192 — номинальный бюджет полной строки одного вопроса, не 8192 токена состояния плюс вопрос. В longdoc-v1 бакет 8k задаёт state 6553–7618 токенов (80–93% номинала; включая state delimiter) и row_limit=8192. Генератор admit проверяет len(state)+max(len(question_branch)) <= T; branch содержит инструкции, все варианты данного вопроса и служебные маркеры. Несколько вопросов — отдельные строки с общим state, не сумма всех вопросов в одном 8k окне. Генератор, manifest, encode/rows_of.
    • 1024 не скрытый лимит longdoc-eval. Это default MAX_BRANCH низкоуровневого encoder (в действительности лимит state+branch). Генератор передаёт явные max_state=65536, max_branch=73728, strict=True, затем отдельно проверяет бюджет бакета. Benchmark берёт context из manifest; LocalPredictor передаёт его в encode через kwargs и проверяет packed limit 139264. Поэтому runtime admission 64k/72k, ограничение конкретного 8k бакета и default 1024 — разные величины; runtime-допуск не доказательство качества. Benchmark, predictor.
    • 7552 — не текущий CLI default обучения. В pinned коде defaults: state=384, row=MAX_BRANCH=1024, packed=2048; training_context(S) прибавляет S−384 к row и packed. При явно выбранном S=7552 получаются row=8192, packed=9216: при максимальном state остаётся 640 токенов на вопрос+варианты+маркеры, не 8192 дополнительных. 7552 сохранён как MAX_TRAIN_STATE_8K и назван карточкой максимальным state релизного обучения; текущий код разрешает поднять training state до 65536, что не переобучает выпущенные веса. Константы и формула, CLI default.
    • Document budgets тоже не равны полному 8192-token state. CFPB documents-v1 отбирает long narratives по 4000–28000 символов (приблизительно 1k–7k токенов), не по 8k токенам; его freezer сохраняет исторический SERVING_CONTEXT_8K: state≤8192 и row≤8192. В longdoc генерации длина измеряется pinned tokenizer Qwen3.8-27B; это нужно отличать от собственного точного подсчёта входа токенизатором KEV-4B. CFPB builder, freezer, контексты, longdoc tokenizer.
    • Что валидировано: по карточке — longdoc-v1 development, CUAD вопросы о контрактах; 8k: 453 вопроса, accuracy 0.837, ECE 0.048. Заранее заданное правило расширения требует полного покрытия и нижней границы 95% CI парной разницы accuracy против 8k ≥−3 п.п. во всех промежуточных бакетах. Для 16k: −1.1 [−3.4; +1.2] п.п., поэтому правило возвращает базовые 8192. Это не гарантия качества любого входа до 8192, не τ-bench и не доказательство переноса на action selection. Правило.
    • Авторские tests подтверждают смысл, не качество на нашей задаче: test_research проверяет совместный рост row/packed budgets, тест validated_context — возврат 8192 при провале 16k и разрыв цепочки допусков; test_longdoc_v1 — labels/window/depth/manifest, причём с имитацией токенов по символам, без весов и токенизатора. Здесь эти tests прочитаны, не исполнялись.

    Узкий вывод: отсутствие summarization/нового retrieval не опровергнуто самим лимитом модели. Достаточность требует фактических token counts фиксированного полного state и каждой строки state+question+options+markers (не только policy или диалога), затем проверки качества на целевых данных. Даже попадание в 8192 устраняет лишь превышение бюджета, а не гарантирует полезность/калибровку. Архитектуру и информацию на входе надо удерживать одинаковыми в RLCD/CE/Brier; решение менять их из этой проверки не следует.

    Воспроизведение и границы личной адаптационной темы

    Измерение воспроизводится следующей командой из корня нашего проекта. Она загружает только заданный Range и tokenizer в память, проверяет SHA256/число полных объектов и печатает агрегаты. Сырые данные и веса не сохраняются в Git.

    SHA256 Range: 4d7f30616a6c158079d1569e8213fbad20518d7725284af197d1383459ebe993. SHA256 tokenizer: fe000e3ed39ed12b8d2481d527d44f93c65d37e87645d2dcc80d1bf9d50d2927.

    Последнее уточнение инициатора 11.10.2026: личное направление — адаптация модели; RLCD против обучения без RL остаётся возможным уточнением после общей схемы. Согласованные направления. Измерение длины не превращает его ВКР в работу о compression/retrieval. Практические варианты — зафиксировать вход общего командного scaffold либо явно ограниченную задачу решений, чей полный вход помещается. Выбор пока не согласован; отбор по длине надо объявлять и показывать coverage, не выдавая поднабор за полный benchmark. τ-knowledge остаётся основным стендом.

    Поднять runtime limit можно без новой архитектуры, но64k admission не равно validated quality; в измеренных историях встречается и больше64k. Input contract и overflow rule одинаковы для сравниваемых способов обучения. Это условие честного сравнения, а не личная новизна вместо исследования адаптации.

    Источники и границы проверки

    Использованы только первичные HF model cards/metadata, исходный код GitHub и существующая постановка проекта. Поиск намеренно ограничен названными моделями; отсутствие найденного M4 Pro benchmark не доказывает, что его нет нигде. Изменившиеся runtime и карточки не переписывают автоматически исторические сведения в других документах. Наличие кода MPS/head-only/full FT отмечено как новое относительно прежнего обзора. Данные τ-bench пересчитаны по полным JSON/AST и Git tree без усечения; большие ответы web_fetch, обрезанные по 100000 символов, не использовались как полный census. Полные ответы прочитаны по HTTP в памяти, без установки/исполнения upstream. Математические расчёты бюджета — сценарные; M4 Pro runtime и деньги здесь не измерялись.
