    Выбор действий в τ-bench при ограниченном контексте

    Статус: статический аудит первичных исходников и собственное измерение токенизации policy; не inference/training benchmark и не утверждённая тема ВКР. Проверен sierra-research/tau2-bench, текущий τ³, commit 4ce7c0397c1eb65c9bbe59aeacfe1ca44a1cd699; дата проверки — 11.10.2026. Область: текстовый half-duplex агент, прежде всего banking_knowledge. Веса не скачивались, зависимости не устанавливались, upstream и платные вызовы не запускались. Скрытые цели задач не использованы для примеров: ниже нет реконструкции банковских test-сценариев.

    Контекст: T-node и E2, ресурсные ограничения, план исследования. Это уточнение контрактов стенда; выбор моделей и подробный план обучения здесь не утверждаются.

    1. Что является следующим действием

    В обычном LLMAgent.generate_next_message модель получает policy, доступные схемы tools и историю, после чего одним генеративным вызовом возвращает AssistantMessage. Вызов generate получает одновременно messages и tools: upstream не выделяет отдельный обязательный классификатор имени. Возвращённое сообщение добавляется в историю. LLMAgent

    Уровень Фактический контракт
    Реплика AssistantMessage.content: текст пользователю, без tool calls
    Один вызов AssistantMessage.tool_calls = [ToolCall(name, arguments, id, requestor)]; arguments — словарь
    Несколько вызовов Тот же AssistantMessage, но список из нескольких ToolCall; это не отдельный тип выходного MultiToolMessage
    Результаты Один ToolMessage либо входной MultiToolMessage(tool_messages=[...]); агент разворачивает пакет в историю

    Правила half-duplex оркестратора требуют текст или tool calls, не оба одновременно. Он поддерживает несколько вызовов в одном сообщении, но _execute_tool_calls исполняет их последовательно циклом, а не обещает параллельный runtime. Поэтому единственный class ID имени не описывает всё пространство native next-message. Схемы сообщений, оркестратор

    Следствия для постановки:

    • Выбор respond не генерирует правильный ответ: нужна отдельная генерация реплики, включая уточнение, объяснение, отказ или завершение обращения.
    • Выбор имени не определяет аргументы, необходимые наблюдения и соблюдение policy. JSON-validity также не доказывает правильность действия.
    • Multi-tool нельзя молча удалить только у исследуемого метода. Для узкого опыта допустим общий single-call режим, явно отличный от native режима; либо общий defer к native агенту для сложного решения.
    • В banking_knowledge solo-режим не поддерживается; убрать диалог с пользователем — не штатный способ упростить этот домен. Environment

    2. Что видно агенту: banking tools

    ToolKitBase.get_tools() исключает @is_discoverable_tool. Такие функции существуют в среде, но их определения не включаются в исходный список схем агента. Это discoverable, а не секретные функции вне области задачи: агент должен узнать о них через KB. Toolkit

    В KnowledgeTools проверенного commit 14 обычных tools:

    • transfer_to_human_agents, get_current_time;
    • get_user_information_by_id, get_user_information_by_name, get_user_information_by_email, change_user_email;
    • get_referrals_by_user, get_credit_card_transactions_by_user, get_credit_card_accounts_by_user, log_verification;
    • give_discoverable_user_tool, unlock_discoverable_agent_tool, call_discoverable_agent_tool, list_discoverable_agent_tools.

    Отдельно объявлены 44 discoverable agent tools, включая учебный example_agent_tool_0000: операции с транзакциями, спорами, счетами, кредитными лимитами и картами. Это инвентаризация реализации, не 44 дополнительных кандидата, разрешённых селектору с первого шага. В отдельном KnowledgeUserTools — 6 обычных и 4 discoverable функции пользователя; они не становятся прямыми инструментами agent-роли. Banking tools

    Retrieval добавляет схемы к этим 14, а не заменяет их:

    Вариант Дополнительные видимые tools Всего исходно
    bm25 KB_search(query) 15
    bm25_grep KB_search(query), grep(pattern) 16
    terminal_use shell(command) 15
    default alltools KB_search_bm25(query, k=10), KB_search_dense(query, k=10), shell(command) 17

    Default alltools использует OpenAI text-embedding-3-large; bm25 — отдельное объявленное условие без этого dense backend. Не путать «все retrieval tools» с раскрытием всех discoverable domain tools. Registry, состав toolkit, retrieval tools

    3. Поиск, открытие описания и исполнение — разные шаги

    1. Найти сведения в KB. KB_search возвращает title, document ID, score и полный content найденного документа: слово excerpts в docstring не означает, что реализация отдаёт только короткий snippet. grep тоже возвращает полное содержимое. В shell-варианте есть отдельное чтение найденного файла и индекс документов; это не универсальный open_tool. Retrieval mixins, shell policy
    2. Открыть agent tool. По явно найденному имени вызвать unlock_discoverable_agent_tool(agent_tool_name). Ответ содержит описание и параметры, разобранные из docstring. Имя сохраняется во внутреннем unlocked-state. Это не добавление новой top-level схемы в список LLMAgent.tools. Banking tools
    3. Исполнить. Вызвать call_discoverable_agent_tool(agent_tool_name, arguments), где внутренние аргументы передаются JSON-строкой, хотя внешние ToolCall.arguments — словарь. Dispatcher проверяет существование функции и предварительный unlock, разбирает JSON и вызывает функцию. Неверные имя/JSON/аргументы дают сообщения об ошибке. Banking tools
    4. Пользовательское действие. give_discoverable_user_tool выдаёт функцию пользователю; затем пользовательская сторона использует call_discoverable_user_tool. Это не agent-вызов той же операции. Banking tools, additional instructions

    list_discoverable_agent_tools() — не поиск по полному каталогу и даже не перечень всех unlocked. Он читает журнал уже вызванных функций в БД. Некоторые дополнительные read-only вызовы туда не логируются: реализация учитывает mutating-функции и отдельный read allowlist оценщика. Unlock сохраняет состояние в памяти, запись в БД происходит при call согласно этому правилу. Не использовать внутренний allowlist как признак модели. Banking tools, Environment

    Policy требует искать имена в KB, не угадывать их, не открывать инструменты «про запас» и получить описание параметров до вызова. Код dispatcher проверяет unlocked-state, но не доказывает, что имя действительно найдено разрешённым способом. Значит, доступность по API и policy-correctness — разные свойства. Additional instructions, Banking tools

    Уточнение к архитектурному shorthand: в текущем commit агент вызывает call_discoverable_agent_tool(agent_tool_name, arguments), а не call_discoverable_tool(name, kwargs). Для содержательного T-node полезны наблюдаемые варианты unlock:<имя> / call:<имя>: иначе все специализированные операции схлопнутся в один ID dispatcher, а выбор настоящего tool останется скрыт в генерации его аргументов. Такое расширение ID — наша факторизация, не новая схема upstream; снаружи нужно восстановить точный native вызов.

    4. Доступная информация и реальный объём контекста

    Для обычного агента допустимы policy выбранного retrieval-варианта, выданные схемы, префикс разговора и собственных вызовов, полученные ответы tools, фактически найденные KB-документы и возвращённые при unlock описания. Текст policy содержит общие ограничения и идентификацию клиента; специфические процедуры лежат в KB, а не обязательно в коротком заголовке. LLMAgent, policy header, additional instructions

    В селектор нельзя передавать скрытое состояние БД, будущие реплики, инструкции user simulator, evaluation_criteria, gold actions и required_documents. Наличие отдельного LLMGTAgent, которому специально показывают resolution steps, не делает такой вход допустимым обычному агенту. golden_retrieval тоже отдельный привилегированный режим: он подставляет task.required_documents, в отличие от standard prompt. LLMAgent / GT agent, prompt builders

    Ниже статический собственный подсчёт текста источников, не токены и не измерение памяти. Policy собрана заменой component placeholders, как в load_prompt_template; для alltools подставлена строка default OpenAI backend. Chars — длина строки, words — разбиение по пробельным символам. Для docstrings убраны пробелы по краям каждой строки, описания соединены двумя переводами строки. Включены Args/Returns; Python-реализация исключена.

    Это не готовый размер модельного запроса: здесь нет сериализованных JSON Schema, имён/типов параметров сверх docstring, system wrapper, истории, tool results и выбранных KB-документов. Описания 44 функций приведены только как инвентарный объём — их нельзя загрузить агенту заранее. Даже короткий набор policy + первоначальные описания не доказывает помещение в маленькое окно: токенизацию надо измерять конкретным tokenizer на фактическом сериализованном входе. Автоматическая обрезка значимых условий policy не является корректной компрессией.

    5. Reference actions не дают единственную метку next step

    Upstream прямо определяет evaluation_criteria.actions как одну reference trajectory. Для DB-оценки она проигрывается в gold environment, чтобы получить целевое конечное состояние. Иная последовательность может привести к эквивалентному состоянию и пройти проверку. Итоговый reward зависит от reward_basis; совпадение actions требуется, когда включён ACTION, а не автоматически у всех задач. Evaluation documentation

    Даже ActionEvaluator проверяет для каждой эталонной записи наличие совпадающего вызова где-либо среди предсказанных tool calls. Этот код не задаёт единственный следующий шаг или обязательный порядок: цикл gold_action → predicted_tool_calls использует compare_with_tool_call. Поэтому нельзя превратить этот список в universally correct next-action labels простым сдвигом на один шаг. Action evaluator

    Для узловой диагностики различать:

    • совпадение с конкретной демонстрацией;
    • принадлежность допустимому множеству следующих действий при данном наблюдаемом префиксе — требует отдельной проверенной разметки;
    • сквозной успех по native evaluator.

    Отсутствие вызова в reference не доказывает ошибку; высокий native reward также не является исчерпывающим аудитом соблюдения всех текстовых правил. Нельзя автоматически объявлять альтернативные поиски, уточнения или порядки read-only проверок отрицательными примерами.

    6. Узкая выполнимая постановка вместо validity gate

    Предложение, уже согласованное по структуре с T/E2, не принятое решение: выбирать одно следующее намерение/имя из наблюдаемого динамического набора плюс respond и технический defer; фиксированная генеративная модель затем заполняет аргументы либо пишет реплику. Для discoverable ветки варианты включают только имена, реально найденные/открытые ранее, с provenance до ответа поиска или unlock. Не оценивать validity готового LLM-вызова под видом самостоятельного выбора действия.

    На первом пилоте разумен banking_knowledge + bm25, без одновременного исследования выбора retriever и без заранее раскрытого каталога. Область single-call/multi-call, упаковка состояния и overflow/fallback должны быть одинаковыми у сравниваемых селекторов. Это не обещание, что весь banking превратится в короткую независимую классификацию.

    Минимальные контроли, продолжающие E2:

    1. Native joint LLM: имя + аргументы/реплика в штатном вызове; исходная точка отсчёта системы, с явно зафиксированным multi-tool режимом.
    2. Факторизованная LLM: LLM выбирает имя/намерение → та же фиксированная модель генерирует аргументы/реплику. Отличие от №1 показывает эффект факторизации и дополнительного вызова, не преимущество маленькой модели.
    3. Дешёвый селектор + тот же generator: сравнение с №2 на одинаковом состоянии, кандидатах и бюджете выделяет замену селектора. Правила или лексический baseline — содержательный дешёвый контроль.
    4. Полный против ограниченного контекста у LLM: отдельная абляция упаковки контекста. Полная LLM против урезанной маленькой модели — сравнение целых систем, не чистый эффект архитектуры селектора.

    Ошибки выбора имени, аргументов, retrieval/discovery и ответа учитывать раздельно; вывод о полезности делать по полному диалогу, стоимости всех вызовов, retries/fallback и задержке, а не только по точности ID. Модели, обучение и объём разметки уточняются в следующих разделах как предложения, а не проведённые модельные эксперименты.

    7. Реально измеренный размер policy в токенах

    Наше собственное статическое измерение 11.10.2026, не оценка «символы / 4». Использован установленный tokenizers 0.22.1, загружены только tokenizer JSON и тексты policy по закреплённым версиям. Веса, Transformers-модели и upstream не запускались; новых зависимостей не устанавливалось.

    Policy без tools и истории Laya English tokenizer Laya multilingual tokenizer KEV / Qwen3.5 tokenizer
    Retail 1527 1452 1454
    Airline 1745 1698 1690
    Banking, BM25 1267 1241 1186

    Retail/airline — исходный текст policy; banking — literal substitution двух component placeholders в BM25 template, без task-specific gold. Использованы tokenizer.no_truncation(), no_padding() и encode(text, add_special_tokens=False). Не включены JSON Schema tools, история, найденные документы, query/options, chat/model wrappers и специальные токены. Поэтому это не полный размер рабочего запроса, а размер одного необходимого компонента.

    Вывод: полные правила уже не помещаются в Laya English512 или typed1024. Числа не доказывают достаточность любого окна 8k для полного эпизода: история, аргументы и retrieved evidence ещё добавятся. Замеры throughput/accuracy не делались.

    from tokenizers import Tokenizer

def count_policy(tokenizer_json, policy_text):
    tokenizer = Tokenizer.from_str(tokenizer_json)
    tokenizer.no_truncation()
    tokenizer.no_padding()
    return len(tokenizer.encode(policy_text, add_special_tokens=False).ids)

def assemble_banking(template, header, additional):
    text = template.replace("{{component:policy_header}}", header)
    text = text.replace("{{component:additional_instructions}}", additional)
    assert "{{component:" not in text
    return text

    Options тоже расходуют контекст, и иногда обрезаются

    Laya упаковывает head (вопрос/варианты) перед state. Реальное место state:

    $$ B_{state}=\max(0,\; max_len-|head|-1). $$

    Поэтому «состоянию всегда остаётся 320/768 токенов» — не точное правило. Option text сначала обрезается до 48 токенов. При нехватке head budget span варианта вместе с MASK получает cap max(4, floor((head_max_len−16)/K)). Инструкция сохраняет минимум 8 токенов, поэтому head_max_len не жёсткий потолок. При большом K head может превышать его. Упаковка. В str/dict сохраняется начало state, в list — конец; это обрезка, не summary. Usage сообщает dropped state и проблемы options. Если markers не помещаются, возникает ошибка. Записывать truncation telemetry; не считать штатную обрезку доказательством, что модель получила необходимые факты. Runtime.

    HTTP Laya допускает до100 choice options, KEV — до255; это API-лимиты, не доказанная точность среди стольких вариантов. У Laya при большом K особенно важны смысл обрезанных описаний и различимость labels. KEV production по умолчанию отклоняет oversized state; явный truncate сохраняет начало, слишком длинная row отклоняется всегда. Laya API, KEV pack.

    Что известно о пригодности к routing

    • KEV0.8: When2Call dev0.167 / test0.133 против four-way chance0.25; model card: «Do not use it for tool-call routing». Поэтому оставить его как дешёвый/отрицательный контроль или объект явно отдельной адаптации, не как основной готовый router. Проверенная карточка.
    • KEV4B: When2Call dev0.660 — реальное узкое основание для пилота, а не аргумент «предупреждения нет». Это не test и не полный τ-bench с args. Карточка.
    • Laya support/domain/model routing и headline typed-decisions accuracy не являются τ-action-selection результатом. В проверенных источниках не найден готовый τ-bench результат этих checkpoints; обзор не претендует на полный citation search. Laya benchmarks.

    Порядок вариантов влияет на обе семьи. У KEV confidence нормирован относительно 1/K, у Laya confidence и answer_confidence различаются. Для calibration брать документированные вероятности и явно выбранное событие, не один универсальный порог для разных K/checkpoints. K также меняет мягкое распределение и фактическую упаковку Laya. KEV API, Laya benchmarks.

    9. Контракт общего узла; не личная тема RLCD

    Актуальная граница после уточнений инициатора 11.10.2026: выбор действий и представления контекста проектируется для общей платформы, а не становится самостоятельной личной темой инициатора. Его направление — адаптация модели; RLCD против обучения без RL — возможное уточнение после общей схемы, не уже обязательный выбор. Согласованные направления, условный RLCD-план.

    Ниже сохранён предложенный технический контракт T/E2 общего стенда вместо verifier. Он пока предусматривает генератор после selector. Разрешение инициатора пропускать LLM на подходящих шагах открывает отдельную развилку карты, но ещё не утверждает fast path. Следующее поручение инициатора — проработать именно варианты полного вызова: контракт ниже сохраняется как контроль name-only → generator, а не итоговая схема сокращения LLM-вызовов. Работа с контекстом и сравнение архитектур не становятся обязательной личной исследовательской программой. Проверка фактической достаточности KEV8192 вынесена в ресурсную оценку.

    Наблюдаемая история + доступные правила/результаты + известные actions
                     ↓
Одинаковый state builder и честно сформированный каталог кандидатов
                     ↓
Selector: правило / LLM / Laya / KEV → ID следующей операции
                     ↓
Fixed generator: только args выбранной операции либо текст ответа
                     ↓
Штатные checks, tools, среда и evaluator τ-bench

    Нет предварительно выбранного большой LLM действия, которое маленькая модель только разрешает. При недостаточной уверенности selector передаёт сам выбор заданной fallback LLM; это техническая обёртка, не новая бизнес-операция.

    Что считать выбранной операцией

    Для обычного tool — его имя; respond покрывает реплику, включая уточнение. Разделить ask_user/respond/finish можно отдельным протоколом разметки, но это наши виртуальные классы, не три готовых native tool names. Для discoverable важен semantic ID конкретной известной функции, а не один общий call_discoverable_agent_tool: если target name по-прежнему выбирает generator, реальное банковское решение осталось у LLM.

    Адаптер переводит выбранный semantic ID в native wrapper и фиксирует target; генератору остаются обычные аргументы. Call-ветка допускает только действительно unlocked функции; отдельный unlock-кандидат — только реально обнаруженное имя. Provenance каталога — наблюдаемые сообщения и результаты discovery, не скрытый список из Python-кода. list_discoverable_agent_tools не считать каталогом всех возможностей: это журнал уже вызванных функций.

    Два честных варианта контекста

    1. Длинный selector: KEV4B или Laya multilingual с явно настроенным окном, измеряемым полным упакованным запросом. Начать с 2k/4k и проверить 8k как отдельный режим; наличие поддержки не заменяет token/accuracy/memory test.
    2. Компактный selector: фиксированное представление наблюдаемых фактов, последних реплик и доступных правил. Его качество является частью метода. Не заполнять поле «следующее действие» или hidden policy flags силами oracle.

    Если состояние строит LLM-summary, она может сама решить задачу, внести ошибки и съесть экономию. Поэтому сначала детерминированное извлечение наблюдаемых ID, результатов, пар вопрос–ответ и явных фактов; непокрываемые состояния — fallback. Нельзя выбросить подтверждение пользователя и ожидать, что RL восстановит факт. Одному и тому же compact state могут соответствовать полные истории с разными правильными действиями: это информационная потеря, не обязательно слабое обучение.

    Все selectors в причинном сравнении получают одинаковый семантический текст и кандидатов, который реально помещается без hidden truncation. Токенизаторы различаются, поэтому равный номинальный max_len не доказывает равенства входов. Long vs compact, полный vs shortlist, predict_long/windowing — разные условия. Для shortlist измерять candidate recall; gold action нельзя подмешивать при пропуске. Полное native сравнение сохраняется даже если compact baseline слаб.

    Ранее предложенный архитектурный пилот — не личный RLCD-план

    Этот список сохранён для общей платформы/тиммейтов. В личном исследовании RLCD не требуется выполнять весь context/model grid до сравнения обучения: достаточно зафиксировать работоспособный вход и единый scaffold.

    1. 100–200 не тестовых состояний для аудита входа: полные lengths по каждому tokenizer/head, число options, потерянные факты, необходимость discovery. Не начинать с 6000 меток и дообучения до проверки информационной достаточности.
    2. Native LLM; factorized LLM full; factorized LLM compact; дешёвый compact selector — одинаковый generator, protocol single/multi-call, candidate source.
    3. Заменить selector на KEV4B и Laya multilingual; English/typed только на реально помещающемся compact input. KEV0.8 — явно отрицательный reference.
    4. Сравнить 2–3 разумных бюджета и seeded перестановки вариантов; не делать полный декартов grid всех размеров/доменов/окон. Проверить потерю критических фактов отдельно от селектора, сохраняя полные наблюдаемые входы для аудита.
    5. Только после этого — сравнение CE/Brier/конкретного RLCD на одной модели с одинаковым входом. Laya logit-RLCD не объявлять OpenJev rationale-RLCD.
    6. Лучшие условия — полный τ-knowledge: task success, выбор/args/discovery errors, fallback, стоимость, p50/p95. Аргументы и ответы по-прежнему требуют генерации; относительно native одного вызова ускорение не гарантировано.

    Разметка меняется, это не переименование binary labels

    Новая запись: (наблюдаемый префикс, view, текущий каталог C, рекомендуемый action или множество приемлемых следующих actions, свидетельства, ambiguities). Для диагностики оценивать попадание выбранной операции в приемлемое множество и отдельно ошибки отсутствующего кандидата. Для categorical CE/Brier нужно заранее определить target distribution q над C: множество допустимых действий само по себе не задаёт единственную «истинную» softmax-вероятность. Равномерное q по множеству — явное правило целевой политики, не установленная вероятность успеха. Imitation одной демонстрации тоже не равна optimal action policy.

    Калибровку выбранного ответа проверять относительно определённого события, например «выбранная операция приемлема при наблюдаемом префиксе», с независимыми labels. Нельзя считать p(action) вероятностью успеха всей траектории. Сохранять grouped splits по исходной задаче/семейству и не превращать соседние шаги в независимые примеры. Native benchmark не предоставляет готовую полную разметку этих множеств; teacher proposals проверяются отдельно.

    10. Как это меняет ресурсы и критерий завершения

    Ориентир 6000 из ресурсной оценки — только порядок возможного объёма adaptation, не подтверждённое достаточное число action labels. Теперь измерять покрытие классов/семейств действий и K, а не баланс yes/no. Для 8k training нельзя переносить память/время короткой Laya из прежней таблицы: более длинные активации требуют нового smoke-test. Mac остаётся основной машиной, но ресурсная выполнимость полного длинноконтекстного обучения не установлена.

    Сохраняется минимум ВКР: агент с заменяемым selector, воспроизводимый protocol, данные и сравнение. Научно полезны и выводы «работает лишь на узком short-context поднаборе», «компрессия определяет потери сильнее модели», «дополнительная факторизация не окупается». Новый RL-алгоритм и полная замена генеративной LLM не становятся обязательными результатами.
